# Town OS Install

Arch-based disk image builder for Town OS. Produces a bootable raw image with a read-only squashfs root, tmpfs overlay, and custom initrd hooks for hardware provisioning.

## Git Remotes

**This repo has TWO remotes, and a push goes to BOTH — every time.** `origin` is `gitea.com/town-os/install` (the branch's upstream) and `github` is `github.com/town-os/install`. Pushing only one leaves the other behind, which is invisible until someone clones the stale one. Don't infer the set from `origin` alone; read `git remote` and push each:

```sh
git push origin main
git push github main
```

```sh
make deps        # install host dependencies (Arch Linux)
make deps-debian # install host dependencies (Debian/Ubuntu)
make image       # build image for TARGET (default: native host arch)
make image TARGET=x86_64   # x86_64 PC (UEFI/GRUB) image
make image TARGET=aarch64  # aarch64 (UEFI/GRUB) image — generic Linux / Apple-Silicon VM
make image TARGET=rpi      # Raspberry Pi (aarch64 native-boot) image
make image TARGET=rg35xxpro # Anbernic RG35XX Pro (Allwinner H700) SD image
make image-container # force the same-arch Arch container build path (native only)
make image-log   # same as image, tee'd into a timestamped log under $(LOG_DIR)
                 # (any build target works: `make <target>-log`, e.g. release-log)
make             # print the target/variable help (the default goal is `help`, not a build)
make run         # build image if stale and launch a libvirt-managed VM
make qemu-fg     # build and launch QEMU with serial console attached
make qemu-usb USB_DEV=/dev/sdX   # boot a physical (already flashed) USB stick in QEMU; no build
make qemu-usb TARGET=aarch64 USB_DEV=/dev/sdX  # ... a foreign-arch stick, under emulation
make serial      # attach to running QEMU serial console (Ctrl-] to disconnect)
make stop        # stop all VMs
make flash        # build image if stale, write to USB
make image-release   # build the image and compress it to .bz2
make build-installer # build the installer OCI image from town-os.img.bz2 (no push)
make push-installer  # build then push to quay.io/town/installer (release-<arch> + dated tag)
make release         # build, compress, and push the installer image (native host arch)
make release TARGET=x86_64   # PC (UEFI/GRUB) release
make release TARGET=aarch64  # aarch64 (UEFI/GRUB) release — generic Linux / Apple-Silicon VM
make release TARGET=rpi      # Raspberry Pi (aarch64 native-boot) release
make release TARGET=rg35xxpro # Anbernic RG35XX Pro (Allwinner H700) release
make clean        # remove current image and VM disks
make clean-images # remove all built images
```

Requires root for image building (make/install.sh uses loopback mounts, chroot, pacstrap) — but `make/image.sh` self-elevates with `sudo`, so invoke `make image` as the normal user and let it prompt. Don't run `sudo make`: that would run the whole build (and any VM launch) as root.

### Arch Linux Setup

```sh
make deps
make image
make qemu-fg
```

### Debian/Ubuntu Setup

Image building requires Arch-specific tools (`pacstrap`, `mkinitcpio`, `arch-chroot`) that have no Debian equivalent. Install host dependencies for VM launching:

```sh
make deps-debian
make image       # builds automatically inside a same-arch Arch container
make qemu-fg
```

On non-Arch hosts `make image` transparently runs the build inside a same-architecture Arch container (see [Container Image Builds](#container-image-builds)). The produced image is this host's architecture — there is no cross-build.

### Fedora Setup (incl. Asahi Remix)

`make deps` auto-detects Fedora (and RHEL/CentOS/Rocky/AlmaLinux) and installs host dependencies via `dnf`. Image building uses Arch-specific tools (`pacstrap`, `mkinitcpio`, `arch-chroot`), so on non-Arch hosts `make image` automatically builds inside a **same-architecture** Arch container — no manual container/transfer step, no emulation. On aarch64 hosts (e.g. Fedora Asahi Remix on Apple Silicon) the build runs as native aarch64 and produces an aarch64 image:

```sh
make deps
make image       # builds inside a same-arch (aarch64) Arch container, native speed
make qemu-fg
```

### Container Image Builds

`make/install.sh` needs Arch-only tools (`pacstrap`, `arch-chroot`, `genfstab`, `mkinitcpio`). On **non-Arch hosts**, `make/image.sh` detects the distro (via `/etc/os-release` `ID`) and dispatches to `make/image-container.sh`, which runs the **unmodified `install.sh`** inside a **same-architecture** Arch container built from `make/Containerfile.build`. The repo is bind-mounted at `/build`, so the finished image is written back to the repo dir on the host. `make image-container` forces this path on any host (including Arch).

- **Always native, never emulated:** the builder container is the host's native architecture (no `--arch`), so it runs at native CPU speed and the produced image's architecture equals the host's. The container exists only to supply Arch's build tooling on a non-Arch distro — it is **not** for cross-building. **The build never inspects, registers, or otherwise touches `binfmt_misc`, and never uses CPU emulation.** If you want a different-architecture image, run the build on a host of that architecture.
- **Base image by architecture:** `image-container.sh` picks the base via `uname -m` — `docker.io/library/archlinux` on x86_64, the third-party `docker.io/menci/archlinuxarm` on aarch64 (the official Arch image is x86_64-only). It is passed to `Containerfile.build` as the `BASE_IMAGE` build ARG. Override with the `BASE_IMAGE` **environment variable**, e.g. `BASE_IMAGE=docker.io/lopsided/archlinux make image` (it flows through `make` → `image.sh` → `image-container.sh` via the environment; no Makefile wiring needed).
- **Architecture in `install.sh`:** `install.sh` selects the kernel package (`linux618` on x86_64, `linux-aarch64` on aarch64), the GRUB target (`x86_64-efi`+`i386-pc` BIOS on x86_64, `arm64-efi` only on aarch64), and the `bios_grub` partition flag (x86_64 only) from `uname -m`. The 1 MiB BIOS-boot partition is still created on aarch64 (unused) to keep partition numbering identical. **zfs is x86_64-only** — there is no prebuilt `linux-aarch64-zfs` module package (aarch64 ZFS would need `zfs-dkms`), so `install.sh` errors if `storage_backend: zfs` on aarch64.
- **Privilege/devices:** the container runs rootful (`sudo podman run`) and `--privileged --cgroupns=host` because `install.sh` uses loopback (`losetup --partscan`), `mount`, and a nested `podman` systemd container (`town-build`). Rootless podman cannot create loop devices, so this must be rootful.
- **DNS is explicit (`--dns`), never inherited from the host's resolver.** `--network=host` (next bullet) otherwise means the container reads the host's `/etc/resolv.conf` — and this repo *rewrites* that file: every `make qemu*` target points the host's systemd-resolved at the dev VM (`make/host-dns.sh`, `VM_DNS`) so the workstation resolves through rolodex. That is the qemu targets' job and it stays, but it must never reach a build: a host that has launched the dev VM would hand a NAT'd guest — possibly down, mid-boot, or unprovisioned — to pacstrap and to every image pull, where it surfaces hours in as an unreachable *mirror* rather than as a DNS problem. `image-container.sh` therefore asks `make/upstream-dns.sh` (see [Build DNS Isolation](#build-dns-isolation)) for the host's **real** upstream servers and passes each as `--dns` on both `podman build` and `podman run`. `--dns` composes with `--network=host` (podman writes the container's own `resolv.conf`), which is exactly the point: keep the host's *routing*, drop the host's *resolver*. `BUILD_DNS='1.1.1.1 9.9.9.9'` pins it; `BUILD_DNS=' '` opts out.
- **Host networking for the build (`--network=host` on both `podman build` and `podman run`):** podman's bridged (netavark) DNS resolves via plain UDP/53 from glibc, which some networks (notably guest/public WiFi) block while still allowing DNS over TCP — the host's systemd-resolved degrades to TCP automatically and keeps working, but a bridged container cannot, so pacman downloads stall with dead DNS. Sharing the host network gives the build the host's full resolver path and also makes it immune to netavark rule flushes caused by `firewall-cmd --reload`. Isolation buys nothing here: the run is already `--privileged`, and the nested `town-build` container uses `--network=none`.
- **Build mirror:** the stock mirrorlist in the aarch64 base image lists the GeoDNS round-robin followed by **European mirrors first**, and pacman walks the list in order — so non-EU hosts download every package from Denmark/Germany. `Containerfile.build` prepends a **US mirror by default** (`ca.us.mirror.archlinuxarm.org` on aarch64, `america.mirror.pkgbuild.com` on x86_64; override with the `BUILD_MIRROR` env var) ahead of the stock list, which remains as fallback, and enables `ParallelDownloads = 5`. The builder's installs, the package prefetch, and `pacstrap` (which inherits the container's mirrorlist, including into the produced OS image) all use it.
- **Nested podman:** the build-time `town-build` systemd container (used to enable units via `busctl`) becomes podman-in-podman. The builder image (`Containerfile.build`) sets podman to `vfs` storage + `cgroupfs` cgroup manager to keep that step reliable.
- Downstream targets (`qemu`, `qemu-fg`, `flash`, `run`) all funnel through the `$(IMAGE)` rule → `image.sh`, so they inherit the build path automatically.

### Emulated aarch64 Builds on x86 (`make image TARGET=aarch64` / `TARGET=rpi`)

Building an **aarch64** (or Raspberry Pi) image on an **x86_64** host is selected with `TARGET=aarch64` (or `TARGET=rpi`) on any build target — `make image TARGET=aarch64`, `make image-release TARGET=rpi`, `make release TARGET=aarch64`, etc. When the requested arch isn't the host arch, the build runs the **unmodified `make/install.sh` inside a full-system `qemu-system-aarch64 -M virt` VM** (`make/image-aarch64.sh` + the guest-side `make/image-aarch64-guest.sh`). On a native aarch64 host these same `TARGET`s build natively (no emulation) — `TARGET` names the *artifact*, and the Makefile picks native vs emulated automatically (`EMULATE`, derived from `TARGET` vs the host arch).

- **This is a deliberate, scoped exception to the "always native, never emulate" rule** — and it does not actually violate the *intent* of that rule. It is emulation of a **whole machine** (`qemu-system`, TCG), **not** `binfmt`/qemu-user and **not** cross-compilation: `install.sh` runs as native aarch64 code inside the emulated aarch64 box, so "image arch == build-host arch" still holds — the build host is simply virtual. `binfmt_misc` is never touched. This is the single mechanism for producing a **non-native** arch image; native same-arch builds keep their fast path (`image.sh` → native or same-arch container) — there is no reason to emulate when native works.
- **How `TARGET` drives it:** `TARGET` is resolved at the **top of the Makefile** into `BUILD_ARCH` (and `RPI` for the Pi flavor) and the derived `EMULATE` flag, so every arch-suffixed default flips to aarch64 at once — the output filename **and** the baked `CONTROLLER_IMAGE`/`ROLODEX_IMAGE`/`UI_IMAGE` tags (`rc.latest-aarch64`). `EMULATE` flips `IMAGE_BUILDER` from `make/image.sh` to `make/image-aarch64.sh`, and rides the `$(IMAGE).bz2 → $(MAKE) $(IMAGE)` sub-make (via `TARGET` propagating on `MAKEFLAGS`) so the whole chain targets the same arch/flavor. A user-set `CONTROLLER_IMAGE` on the command line still wins. **Model: import a cached build environment, run the build, export the image.**
- **Cached build-env** (`.build-env/`, git-ignored): built once from the same `menci/archlinuxarm` base the aarch64 container build uses. `podman pull --arch arm64` + `podman export` assemble the rootfs with **no aarch64 execution on the host** (pull/export only download and unpack), written to an ext4 disk via `mkfs.ext4 -d` (no loop mount). The build toolchain (same set as `Containerfile.build`) is `pacstrap`/`pacman`-installed on the **first VM boot** and persists on the cached disk; later builds skip provisioning. Delete `.build-env/` to force a clean rebuild. **A build failure keeps the cache; only an *unreported* exit discards it.** `image-aarch64-guest.sh`'s `finish()` ends every exit path — `BUILD_FAIL` included — with an emergency sync + a read-only remount of every filesystem, so a disk that reported a status is consistent on disk (and its keyring is re-verified, and rebuilt if it doesn't check out, on the next boot). No status file at all means qemu died, the guest panicked, or the host killed it — that disk was powered off still mounted rw and can carry a half-written pacman DB/gnupg keyring, which fails the *next* build at `pacman -Sy` with "GPGME error: No data"; that is the only case that is discarded (as is a Ctrl-C, whose trap discards too).
- **Boot mechanism** (the one fragile, **unverified** piece — like `RPI=1`, correct-by-construction but not yet booted here): the VM always **direct-kernel-boots** (`-kernel`/`-initrd`, no UEFI) with a `linux-aarch64` kernel and a **from-scratch initramfs assembled on the host** (static Alpine busybox + the virtio/ext4 `.ko` modules extracted from the kernel package — all file assembly, no aarch64 execution). The initramfs `insmod`s virtio-blk + ext4 and pivots into the ext4 build-env; everything else (net, 9p, loop) is `modprobe`d from the rootfs after `switch_root`. Expect to iterate the initramfs module set on the first real run.
- **Repo I/O:** the repo is shared into the guest **read-write over virtio-9p** (tag `repo`; no virtiofsd needed — 9p is built into qemu). The guest copies the repo to local ext4, runs `install.sh` there (9p cannot reliably back the loop device `install.sh` needs), and **copies the finished image back onto the 9p share**, where it lands in the repo dir on the host (chown'd to the invoking user). Networking is QEMU user-mode (SLIRP) — outbound `pacstrap`/image pulls work with no host bridge. Build status returns via `.build-env/guest-status`. **`.kernel-cache/` moves in both directions over that share**, which is what keeps a failed RG35XX build from costing the kernel: the staging `rsync` carries the host's cache *into* the guest (so `install.sh` reuses a kernel it built on an earlier run), and `finish()` copies new entries back *out* to the host repo dir on **every** exit path — success or failure — before unmounting. Without the outbound half, `install.sh` writes the cache to `/root/build` on the build-env disk, and anything failing after the kernel (configure.sh, U-Boot, squashfs) took hours of kernel build with it. Entries are content-keyed, so the copy is `--ignore-existing`. **The outbound `rsync` must pass `--no-owner --no-group`**: the share is exported `security_model=none` and qemu runs *unprivileged*, so the 9p server cannot `chown` anything to the guest's root — plain `rsync -a` gets EPERM on the destination directory itself, exits 23, and the cache silently never reaches the host, which is the entire failure the outbound half exists to prevent. Ownership is not wanted anyway: the files land owned by the invoking user, which is correct.
- **The guest network is a RANDOM free /24, and its DNS bypasses SLIRP's proxy.** QEMU user-mode networking hardcodes `10.0.2.0/24`, which is a guess rather than a reservation — a host (or VPN) that actually uses it makes the guest's own addresses shadow the network it is NAT'd onto. The SLIRP net is private to the qemu process, so `image-aarch64.sh` picks a random RFC1918 `/24` **the host has no route into** (probe: `ip route get <net>.1` must answer `via <gw>`; 40 tries, then falls back to `10.0.2.0/24` with a warning) and passes it as `-netdev user,net=…,host=…,dns=…`. `BUILD_NET=a.b.c.0/24` overrides. **The dev VM's `192.168.122.0/24` never appears on this path** — that subnet belongs to the qemu targets. DNS is separate and more important: SLIRP's built-in proxy (`<net>.3`) forwards using the **host's** `/etc/resolv.conf`, which `make qemu*` repoints at the dev VM, so a build VM using it resolves through a guest that may be down. The guest is instead handed the host's real upstream servers (`BUILD_DNS`, from `make/upstream-dns.sh`); SLIRP NATs those queries out exactly as the host would send them, and the proxy remains only as the fallback when nothing could be discovered. **The addresses reach the guest through `guest-params.env`, and `image-aarch64-guest.sh` re-applies them on every boot** — `/sbin/town-init` is baked into the *cached* build-env disk, so a disk provisioned before this change still hardcodes `10.0.2.x`; the repo-tracked guest script flushes the interface and reconfigures, which is what keeps an existing `.build-env/` working instead of silently booting with no route.
- **Slow:** TCG emulation, no KVM (foreign arch on an x86 host). Expect a long first run (provisioning + build).

### Build DNS Isolation

**DNS is isolated per task in this repo. Only the `qemu*` targets touch the host's resolver — and no build path depends on it.**

The two halves are deliberate and must not be merged. `make qemu*` points the host's systemd-resolved at the guest (`VM_DNS` → `make/host-dns.sh`) so the workstation resolves through **rolodex** exactly as a real client would; that is [the whole point of those targets](#host-dns-through-the-vm-vm_dns). The consequence is that a workstation which has ever launched the dev VM has a resolver that is a NAT'd guest — one that may be powered off, mid-boot, unprovisioned, or (on `qemu-usb` against a blank stick) never coming up at all. Anything that reads `/etc/resolv.conf` inherits it, and an image build is the worst possible inheritor: it fails **hours in**, and it fails looking like a broken package mirror rather than like DNS.

- **`make/upstream-dns.sh` is the SINGLE discovery implementation**, shared by the build paths *and* by `qemu.sh`'s libvirt `<forwarder>` logic (which had its own copy of this pipeline; there is now one). It prints the servers the **host itself** got from the local network, in order: NetworkManager's per-link `IP4.DNS` on the default-route interface → systemd-networkd lease files → dhcpcd's `/run/dhcpcd/resolv.conf` fragments → non-loopback entries in `/etc/resolv.conf` → the default gateway. **DHCP-provided values come first on purpose**: NetworkManager keeps the per-link record even while resolved is overridden to point at the guest, so those survive exactly the condition this exists for.
- **What it can never return:** loopback (so resolved's stub — and therefore the VM behind it — cannot come through `/etc/resolv.conf`), `0.0.0.0`, and any address inside a subnet owned by a **local virtual bridge** (`virbr*`, `podman*`, `docker*`, `br-*`). That last filter is computed from `ip addr`, not hardcoded, so a renumbered libvirt network or a non-default `VM_BRIDGE` is covered without anyone remembering to update a constant. `--exclude`/`--exclude-net` add more; `--fallback` appends public resolvers **after** the discovered ones (so on a network that filters outbound :53 the local resolver still answers first).
- **Each build path applies the list with the only mechanism it has:**
  - **Native Arch build** — `make/build-dns-ns.sh` runs `install.sh` inside a private **mount namespace** (`unshare --mount --propagation private`) whose `/etc/resolv.conf` is a bind of ours. glibc has no per-process resolver, so this is the equivalent primitive. The host's real file is **never modified** and the bind dies with the build, which keeps the repo's "builds have no host side effects" rule intact. Everything spawned inherits it — including the chroot, since pacstrap copies the visible `resolv.conf` into the image, so the in-chroot kernel/U-Boot builds and their `curl` fetches resolve the same way. An empty list, a missing `unshare`, or a failed bind all **fall through to running the build unchanged**; this never blocks a build.
  - **Container build** — `--dns` on both `podman build` and `podman run` (see [Container Image Builds](#container-image-builds)).
  - **Emulated aarch64 VM** — the servers are written into the guest's `/etc/resolv.conf` instead of SLIRP's DNS proxy (see [Emulated aarch64 Builds](#emulated-aarch64-builds-on-x86-make-image-targetaarch64--targetrpi)).
  - **Installer image** — `podman build --network=none` in `push-installer.sh`. That image is `FROM scratch` + one `COPY`, so the correct isolation is *no network at all*. (`podman push` afterwards is a host process on the host's network; nothing container-side can isolate that.)
- **`BUILD_DNS` overrides everything** (`BUILD_DNS='1.1.1.1 9.9.9.9'`), and **`BUILD_DNS=' '` opts out** — a non-empty blank string is falsy to every consumer here, so each path falls back to inheriting the host's resolver as before. `make/image.sh` resolves it once and exports it, so the native and container paths under it never discover twice.
- **Subnets follow the same rule.** The emulated build VM gets a random free RFC1918 `/24` rather than QEMU's hardcoded `10.0.2.0/24` (`BUILD_NET`), and `192.168.122.0/24` appears **only** in the qemu targets.
- **Neither variable belongs in `.build-config`, and neither is threaded through the Makefile recipe** (they are environment variables, like `BASE_IMAGE`/`BUILD_MIRROR`). They describe *how the build reaches the network*, not what ends up in the image — stamping them would invalidate a perfectly good image every time the workstation changed WiFi networks.

### Raspberry Pi Images (`RPI=1`)

`RPI=1 make image` (equivalently `make image TARGET=rpi`) builds a **native-boot Raspberry Pi image** for **Pi 4 / 400 / CM4 and Pi 5 / CM5** (one image covers all of them). The Pi build has a **distinct default filename** (`town-os-<date>-aarch64-rpi.img` vs the normal `…-aarch64.img`), so it is a separate artifact that coexists with the UEFI/GRUB image instead of clobbering it; `make flash RPI=1` / `make qemu RPI=1` resolve to the `-rpi` image automatically. The Pi's GPU bootloader reads only a FAT partition and loads the kernel/DTB/initramfs directly, so this path is fundamentally different from the UEFI/GRUB image and is gated entirely behind the `RPI` flag (threaded `make` → `image.sh`/`image-container.sh` → `install.sh`, and stamped into `.build-config` so toggling it forces a rebuild). It is **aarch64-only** and **btrfs-only** (zfs is rejected). **Bare `RPI=1` builds natively** — build on an aarch64 host such as Fedora Asahi; `RPI=1` on x86_64 errors out. To cross-build a Pi image on an x86_64 host, use **`make image TARGET=rpi`** (`TARGET=rpi` implies `RPI=1` *and* selects full-system aarch64 emulation). The standard image (x86_64 + qemu `virt` aarch64) is unchanged when `RPI` is empty and `TARGET` is native.

What the Pi build does differently (all in `make/install.sh`, behind `if [ -n "$RPI" ]`):

- **Kernel:** ALARM **`linux-rpi`** (RPi Foundation kernel, 4 KB pages) instead of `linux-aarch64`. It ships a single `/boot/kernel8.img` that boots **both** Pi 4 and Pi 5 with a uniform page size (vs Raspberry Pi OS's per-board 4 K/16 K split), the flat `*.dtb` board files, and `overlays/`. `linux-rpi-16k` (16 KB) is Pi 5-only and is **not** used — it won't boot Pi 4.
- **Firmware:** adds **`raspberrypi-bootloader`** (the GPU firmware: `start4.elf`/`fixup4.dat` used by Pi 4; the Pi 5 firmware lives in its SPI EEPROM and ignores these).
- **No GRUB, no UEFI.** Both `grub-install` calls and `grub.cfg` are skipped. Instead the FAT partition (enlarged from 64 MiB to **512 MiB** so it can hold the kernel + initramfs + DTBs + overlays + firmware) is staged with `kernel8.img`, `initramfs-linux.img`, the DTBs/overlays, the firmware blobs, and a generated `config.txt`, `cmdline.txt`, and `autoboot.txt`. The partition table stays **GPT** with the existing 3-partition layout (recent Pi 4/5 EEPROMs read 512-byte GPT; the unformatted 1 MiB part1 is skipped and `autoboot.txt` pins `boot_partition=2`); the data partition is still part3, so all the downstream shrink/squashfs/fstab machinery is untouched.
- **`config.txt`:** `arm_64bit=1`, `enable_uart=1`, `initramfs initramfs-linux.img followkernel`, `dtparam=pciex1` (enables PCIe so an NVMe root works on Pi 5; no-op on Pi 4), plus board-gated **USB current** knobs — `usb_max_current_enable=1` under `[pi5]` (lift the 600 mA total port cap to the full ~1.6 A even when the PSU doesn't advertise 5 A) and `max_usb_current=1` under `[pi4]` (raise the 600 mA cap to 1.2 A), with an `[all]` reset before `[tryboot]` so the Sledgehammer cmdline stays board-agnostic. Each USB knob is silently ignored by the other board's firmware; both matter because a from-USB install image is exactly what browns out bus-powered SSD/NVMe adapters, hubs, and hungry sticks. `config.txt` can't override the PSU-negotiation check itself — for that, set `PSU_MAX_CURRENT=5000` in the **EEPROM** (see [Flashing & booting](#raspberry-pi-images-rpi1)). The firmware auto-selects the correct board DTB — no `device_tree=` needed.
- **`cmdline.txt`:** `console=serial0,115200 console=tty1 root=UUID=<data> rootfstype=ext4 rootwait rw`. **`serial0` is deliberate** — the firmware rewrites it to the board's real UART (**`ttyS0` on Pi 4, `ttyAMA10` on Pi 5**), so do NOT hardcode the qemu `ttyAMA0` here. `root=UUID=` is exactly what the `town-squashfs` initrd hook expects (the loop-mounted `root.sfs` flow is unchanged).
- **Serial getty:** because the live serial device is per-board, the build enables `town-os-serial-getty@` for **all three** candidates (`ttyS0`, `ttyAMA0`, `ttyAMA10`) and gates each on its own console via the `%I` specifier (`ConditionKernelCommandLine=console=%I,115200`), so only the one matching the live `console=` starts. The stock `serial-getty@` for those three is masked.
- **Pi drivers in the initrd:** `scripts/configure.sh`'s `WANT_MODULES` gains the Pi storage/USB/PCIe/net drivers (`sdhci_iproc`, `pcie_brcmstb`, `xhci_pci`, `dwc2`, `bcmgenet`, `macb`, …). The existing `modinfo` filter keeps only those present for the installed kernel, so this is a no-op on the non-Pi builds and silently drops any built-in (`=y`) or absent module on the Pi build.
- **Sledgehammer** keeps working without GRUB via the Pi firmware's **`tryboot`** one-shot: `config.txt` has a `[tryboot]` section selecting `cmdline_sledge.txt` (= the normal cmdline plus `town.sledgehammer`). A `reboot "0 tryboot"` boots that once and auto-reverts on the next boot, so `town.sledgehammer` reaches `/proc/cmdline` exactly as the old GRUB entry did and **`town-os-sledgehammer.service` / the getty consumers are unchanged**. The ttyforce *trigger* picks the mechanism per platform: `scripts/ttyforce-getty.sh`/`ttyforce-status.sh` detect a Pi via `/proc/device-tree/model` and pass `--sledgehammer-tryboot` (ttyforce then runs `reboot "0 tryboot"`) instead of `--sledgehammer-grub-entry` (grub-reboot).

**Flashing & booting (user-run; Claude never builds or flashes):** write the image to an SD card, USB stick, or NVMe with `dd` (or `make flash USB_DEV=/dev/sdX`). For **Pi 5 NVMe boot**, also set the EEPROM boot order to include NVMe (`rpi-eeprom-config --edit` → `BOOT_ORDER=0xf416`; add `PCIE_PROBE=1` for non-HAT+ adapters) — `dtparam=pciex1` is already in `config.txt`. Serial console is on the Pi's UART at 115200 (Pi 4 GPIO 14/15; Pi 5 the 3-pin debug header).

**USB power (bus-powered SSD/NVMe adapters, hubs, hungry sticks):** `config.txt` already lifts the firmware's default USB current cap on both boards — `usb_max_current_enable=1` (Pi 5, `[pi5]` → full ~1.6 A) and `max_usb_current=1` (Pi 4, `[pi4]` → 1.2 A) — so no user action is needed for the common case. `config.txt` cannot raise the cap **higher** than the port maximum, though: if a Pi 5 still browns out a peripheral with a genuine 5 A PSU, the firmware only unlocks the full current when it can confirm the PSU's capability, which some third-party supplies don't report — force it in the EEPROM with `rpi-eeprom-config --edit` → `PSU_MAX_CURRENT=5000` (this is a **bootloader** setting, distinct from the `config.txt` knob, and is the only way to override the PSU-negotiation check). Verify the runtime state on a booted Pi 5 with `vcgencmd get_config usb_max_current_enable` and `vcgencmd pmic_read_adc` (per-rail current).

**Unverified on hardware:** this path is correct-by-construction from the firmware/ALARM docs but has not been built or booted on a real Pi — expect to iterate the exact initrd module set and the Pi 5 serial-getty device on first boot.

### Anbernic RG35XX Pro Images (`RG35XX=1` / `TARGET=rg35xxpro`)

`make image TARGET=rg35xxpro` (equivalently `RG35XX=1 make image` on an aarch64 host) builds an **SD-card image for the Anbernic RG35XX Pro** and the rest of the **Allwinner H700** handheld family (RG35XX Plus / H / SP / 2024 — one image covers them all, since only the device tree differs). Like the Pi build it gets a **distinct filename** (`town-os-<date>-aarch64-rg35xxpro.img`), a **separate installer tag** (`release-aarch64-rg35xxpro`), and is gated entirely behind the `RG35XX` flag (threaded `make` → `image.sh`/`image-container.sh` → `install.sh`, stamped into `.build-config`). **aarch64-only and btrfs-only.** Bare `RG35XX=1` builds natively (aarch64 host); `TARGET=rg35xxpro` on x86_64 selects the same full-system emulation path as `TARGET=rpi`.

**The device requires the boot card.** The RG35XX Pro has *no* internal storage — the image goes on the card in the **TF1** slot, which is the only slot the SoC boots from (MMC0). TF2 is not a boot device.

**Why this target is structurally different from every other one:** an Allwinner box has *no* firmware that can boot an OS. There is no UEFI (unlike the PC/qemu images) and no GPU bootloader reading a config file (unlike the Pi) — the BootROM does exactly one thing, which is to look for a bootloader in **raw sectors** of the boot card. So this is the only target whose image must **carry a bootloader, built from source during the image build**:

- **U-Boot + TF-A are compiled in the chroot** by `scripts/build-uboot-rg35xx.sh`, invoked from `install.sh` *before* `configure.sh` (which is what strips the toolchain back out — a build placed after it would have no compiler). **TWO bootloaders are built, one per DRAM type** (`RG35XX_DRAM`, default `lpddr4`): the SPL initialises memory from compiled-in timings and H700 handhelds shipped with **both LPDDR3 and LPDDR4**, so the wrong timings mean the board never brings RAM up — dead at power-on, no output at all. Mainline carries only a single (LPDDR4) defconfig, which is why ROCKNIX ships two U-Boot builds for this SoC; we use their pinned `lpddr3`/`lpddr4` defconfigs and DRAM patch and build both. The selected one is written to the raw sectors and **both are staged on the boot partition**, so a mis-guessed unit is rescued by re-writing 128 KiB of the card (`dd … seek=128`) instead of rebuilding. Mainline U-Boot's H700 support covers the whole lineup; the H700 has no TF-A platform of its own, so BL31 is built with `PLAT=sun50i_h616` (the H700 is an H616 derivative) and passed to U-Boot as `BL31=`, producing `u-boot-sunxi-with-spl.bin`. `SCP=/dev/null` skips the optional Crust firmware (its feature is SCP suspend/resume, which a headless appliance never uses). The build pulls pinned tarballs (`UBOOT_VERSION`, `ATF_VERSION`) and installs/removes its extra build deps (`bc dtc swig python python-setuptools` — python + swig are **not** optional: the sunxi image is assembled by binman, which needs pylibfdt built from the U-Boot tree). `UBOOT_BIN=<path>` skips the build entirely and uses a prebuilt blob.
- **The bootloader is written at 128 KiB (sector 256), not the traditional 8 KiB — and that choice is what lets this target keep GPT.** 8 KiB lands *inside* the GPT partition-entry array (LBA 2–33) and would destroy the partition table, which is why nearly every sunxi distro image is MBR. But every ARM64 Allwinner SoC checks sector 16 **and then** sector 256, and 128 KiB is past the whole GPT — so the image keeps the identical GPT 3-partition layout, and the shrink/`sfdisk`/squashfs machinery is untouched. Part1 moves out to **4 MiB** (`PART1_START_MIB`) to leave ~3.9 MiB of raw space, and the build **fails** if `u-boot-sunxi-with-spl.bin` would overrun it. The `dd` runs **last**, straight into the image file after the final `sfdisk` restore, so nothing that rewrites the partition table can land on top of it.
- **U-Boot then boots via `extlinux`**, not GRUB and not `boot.scr`: `/extlinux/extlinux.conf` on the FAT partition (enlarged to 512 MiB like the Pi's, since it holds the kernel and initramfs) with `LINUX /Image`, `INITRD /initramfs-linux.img`, `FDT /<dtb>` and `root=UUID=<data>` — exactly what the `town-squashfs` hook expects. U-Boot's bootstd/syslinux bootmeth finds it by scanning partitions, so no `mkimage` and no boot script are involved.
- **The kernel is the stock ALARM `linux-aarch64`** — the same generic multiplatform kernel the qemu/UEFI aarch64 image uses. It already carries `ARCH_SUNXI`, the H616/H700 clocks, `MMC_SUNXI`, the AXP717 PMIC and the board's RTL8821CS SDIO WiFi driver, and installs the Allwinner DTBs under `/boot/dtbs/allwinner/`. Nothing board-specific is patched in; only the boot path differs.

**The screen is the console — there is no serial console in this image at all.** The cmdline is `console=tty0` and nothing else, no serial getty is enabled, and `make image TARGET=rg35xxpro` needs no other variable to produce that. Kernel messages, the ttyforce installer and the login getty all land on the handheld's own panel, driven by its own buttons. Two things had to be true for that, and both are built here:

1. **A PATCHED KERNEL, because mainline cannot light this panel.** Mainline drives nearly all of this board but not the display: it has the DE33 mixer (`sun8i_mixer.c` knows `allwinner,sun50i-h616-de33-mixer-0`) and nothing else — no H616 display-engine compatible in `sun4i_drv.c`, no LCD timing controller, and `sun50i-h616.dtsi` has no display/mixer/TCON nodes at all. The work was posted upstream in July 2025 (`arm64: dts: allwinner: h616: add LCD timing controller and display engine support`, v2, 12 patches) and has **not landed**, so no device tree can fix this on a stock kernel. `scripts/build-kernel-rg35xx.sh` builds a pinned upstream tree plus the **GPL H700 patch set ROCKNIX maintains** (pinned by commit): display engine, TCON, the generic MIPI-DPI/SPI panel driver, the PWM driver and backlight the panel needs to be *visible*, and USB OTG host mode. **The kernel pin (`KERNEL_VERSION`/`KERNEL_SHA256`, a kernel.org tarball) and `ROCKNIX_COMMIT` must move together** — the patch set touches `drivers/gpu/drm/sun4i` and the Allwinner DTs, so a mismatched pair fails the build on a patch that won't apply. Read the right kernel version from **`projects/ROCKNIX/packages/linux/package.mk`** (`case ${DEVICE} in H700)`) — the root `packages/linux/package.mk` is a decoy that the project-level file shadows, and its versions (keyed on `${LINUX}`) are never what an H700 image is built from. There is no stock-kernel option — an image with neither display nor serial would have no console at all.
2. **The buttons stay a GAMEPAD, because that is what ttyforce wants.** ttyforce (>= 0.5.1) reads the pad directly through gilrs/evdev and drives the whole installer from it: D-pad navigates, **Start raises an on-screen keyboard**, the face buttons type on it, L2 shifts, L1/R1 page. So the device tree's `BTN_SOUTH`/`BTN_DPAD_*` mapping is left alone — re-mapping those lines to `KEY_*` would make gilrs stop seeing a gamepad at all, the OSK could never be raised, and a board with no keyboard and no serial console would have no way to type a WiFi password. **Text entry therefore needs no USB keyboard.** The pad itself comes from ROCKNIX's out-of-tree **`rocknix-singleadc-joypad`** driver (next bullet), not mainline `gpio-keys`. `dts/…-rg35xx-pro.dts` changes exactly two things:
   - **A and B are swapped.** The kernel names face buttons by POSITION, so the physical A (right) is `BTN_EAST` and B (bottom) is `BTN_SOUTH`; ttyforce follows the other convention, where South is accept. Composing them would put "accept" on the button printed B. The swap makes the printed labels mean what they say.
   - **Menu becomes `KEY_A`.** ttyforce's getty blanks the panel after five minutes and only watches input devices advertising `KEY_A` — its "this is a keyboard" test — so a pure gamepad is invisible to it and *nothing on the device could wake the screen*: no keyboard, no serial, just a dark panel that reads as a dead box. One `KEY_A` qualifies the device, after which the watcher counts every event from it (gamepad buttons included) as activity. `BTN_MODE` is unmapped by ttyforce, so Menu is the button to spend; the cost is that Menu types an "a" into a focused text field. **The cleaner fix is upstream** — teach `src/tui/getty.rs` about the gamepad `src/tui/app.rs` already handles; the getty has no gamepad support today, so its menus are also un-navigable from the device (it still displays fine).

   `configure.sh` **fails the build if the installed ttyforce is older than 0.5.1**, because on this board that silently produces an installer nobody can type into — a failure that would otherwise surface in front of a user halfway through provisioning. It reads the version from **`cargo install --list`**, never from `ttyforce --version`: ttyforce's clap `Cli` declares no `version`, so that flag is an unknown argument and exits 2 — which, under `configure.sh`'s `set -e -o pipefail` and with stderr going to `/dev/null`, killed the whole build with **no message at all**, hours in and immediately after the kernel and U-Boot were built. `cargo install --list` reports the version for both the crates.io and the `--git` install path and cannot be broken by the binary's CLI.

Consequences worth keeping in mind: the display is now a **hard dependency of provisioning**, which is why the build verifies the panel node survives into the compiled DTB and why the kernel config check is strict. And `make qemu-usb TARGET=rg35xxpro USB_DEV=…` is the one emulation path that shows what a user actually sees — the patched kernel has `virtio_gpu`, so the guest paints the GTK window the way the real device paints its LCD.

- **The joypad driver is built too, and it is the board's ONLY input device.** Patch `0140` replaces the DT's mainline `gpio-keys` gamepad with a `rocknix-singleadc-joypad` node bound to ROCKNIX's out-of-tree driver (`github.com/ROCKNIX/rocknix-joypad`, pinned by `JOYPAD_COMMIT`), which the kernel build compiles as an external module (`make M=… DEVICE=H700`, installed under `modules/<kver>/extra`, in the initrd via `configure.sh` and asserted by `verify_initrd`). WHY take an out-of-tree driver: it is the only thing that reads the **analog sticks** — they sit behind a GPIO-selected ADC mux that no mainline binding walks — and it presents buttons and both sticks as one device, which is what gilrs wants. Four things travel with that decision, none optional:
  - **`0144` must be applied with `0140`.** It is only `&joypad { amux-count = <4>; }` on the `-h` board, and `joypad` is a label `0140` creates: keeping one without the other doesn't fail to apply, it fails later at **DTC** ("Label or path joypad not found") and takes **every Allwinner DTB** with it. `RG35XX_KERNEL_PATCH_SKIP` still exists but now defaults to empty; anything added to it has to be checked for dependents.
  - **Three patches from *other* ROCKNIX patch dirs** (`packages/linux/patches/{mainline,rocknix-joypad}`, `EXTRA_PATCHES` in the script, applied before the device dir): `input-polldev` (deleted from mainline; the driver registers a polled device), the `gpiolib-of` revert that restores `of_get_named_gpio_flags()` + `<linux/of_gpio_legacy.h>`, and the **adc-keys** patch that defines and `EXPORT_SYMBOL`s `joypad_input_g` — the one symbol the driver declares `extern` and never defines. Without the last one the module compiles and then **refuses to load** on an unresolved symbol.
  - **`CONFIG_KEYBOARD_ADC`, `CONFIG_INPUT_POLLDEV`, `CONFIG_INPUT_FF_MEMLESS`, `CONFIG_IIO`, `CONFIG_SUN20I_GPADC`** are all built in (matching ROCKNIX's own H700 config). `KEYBOARD_ADC` is not for any button on this board — it is where `joypad_input_g` lives. `INPUT_FF_MEMLESS` is needed because the driver references `input_ff_create_memless()` even though this board has no rumble motor.
  - **`CONFIG_WERROR` must be off.** `-Wmissing-prototypes` and `-Wunused-result` are on by default and ROCKNIX's patches trip both (their adc-keys change adds two prototype-less non-static functions; their OTG fix ignores `regulator_enable()`'s return). With `-Werror` that is a dead build hours in; ROCKNIX unsets `WERROR` for the same reason.

  The patch set is applied **in filename order as a sequence** (later patches edit DT nodes earlier ones create), and any patch that fails to apply **stops the build naming itself** rather than yielding half a display stack.
- **Config base is the kernel's own `arm64 defconfig`, not ALARM's config**, plus **`kernel/rg35xxpro.config`** — a tracked kconfig fragment merged on top with `scripts/kconfig/merge_config.sh -m`, then resolved by a single `olddefconfig`. WHY defconfig as the base: ALARM's config tracks a far newer kernel than this patch set applies to, so `olddefconfig` against it would silently default hundreds of symbols that moved in between — on a board that cannot be recovered without a soldering iron. WHY a fragment rather than a checked-in `.config`: a whole `.config` rots the moment the kernel pin moves and its diffs say nothing about intent, whereas a fragment states only the decisions this board makes and lets `olddefconfig` resolve the rest against the kernel actually being built. `RG35XX_KERNEL_CONFIG=<path>` overrides it for a one-off experiment.
  - **Most of that file is subtraction, and that is the point.** `arm64 defconfig` is the **multiplatform** config: it enables essentially every ARM64 vendor's driver tree, mostly as modules. Under the emulated build (`TARGET=rg35xxpro` on x86, where the whole compile runs under TCG) that meant **hours** spent compiling MediaTek clocks, Tegra audio, NVIDIA host1x, UBIFS and NFC for a handheld that has none of them. The fragment switches off every `ARCH_*` platform but `ARCH_SUNXI` — which, because vendor drivers are gated on `depends on ARCH_x || COMPILE_TEST` and defconfig sets no `COMPILE_TEST`, takes their clocks, pinctrl, SoC glue, PHYs, thermal, DRM and audio with it — plus the subsystems the appliance never uses (sound, Bluetooth, NFC, V4L/DVB, InfiniBand, staging, MTD, KVM, 32-bit `COMPAT`), the filesystems it never mounts, and all of `ETHERNET` (one symbol for all of `drivers/net/ethernet`; **USB Ethernet and virtio_net are not under it** and are unaffected).
  - **A second, separate round of subtraction targets what `ARCH_*` pruning cannot reach.** Switching platforms off only drops drivers that declare `depends on ARCH_x`; a large amount of defconfig hangs off subsystem menus instead and survives untouched. The fragment therefore also prunes, by category: **DRM panels and bridges** (~55 modules — `DRM_PANEL_*` and the HDMI/DSI/eDP bridge chips depend on `DRM_PANEL`/`DRM_BRIDGE` + OF/I2C, *not* on any `ARCH_` symbol, so enabling DRM at all kept every one of them compiling; this board has one DPI panel and no bridge), plus `DRM_PANTHOR`/`DRM_POWERVR` which the older LIMA/PANFROST lines never covered; **ACPI and EFI** (both boot paths are device-tree — U-Boot's extlinux bootmeth uses `booti`, and `make qemu-usb TARGET=rg35xxpro` direct-kernel-boots with no pflash, so neither firmware interface is ever entered); **device-mapper and md RAID** (ttyforce implements all three of its layouts — Single/RAID1/RAID5 — with `mkfs.btrfs` alone and never calls mdadm, LVM or cryptsetup, and podman uses the native btrfs driver); the **USB controller families and gadget functions** this board lacks (DWC2/DWC3/ChipIdea/ISP1760/MTU3/Cadence/Renesas, plus USB-C `TYPEC`/TCPM/UCSI — `USB_GADGET` itself stays because `USB_MUSB_DUAL_ROLE` selects it); **all SDHCI host drivers** (`MMC_SDHCI` is the parent symbol for ~15 of them; the board's host is `sunxi-mmc`); UFS, NVMe and NBD; `NET_SCHED`/DSA/IPVS/`IP_PNP` and the Ethernet **PHY** drivers (PHYLIB survives `# CONFIG_ETHERNET is not set` and is still needed by `smsc95xx`, but the discrete PHY chips are not); appliance-irrelevant kernel features (NUMA, memory hotplug, KSM, hibernation, kexec/crashdump, audit, quota, BFQ, SMMU/VFIO); and other people's platform glue (ChromeOS EC, Greybus, SPMI, RP1, PCI SR-IOV/endpoint/AER/hotplug).
  - **`CONFIG_EFI_PARTITION` is NOT part of the EFI pruning and is asserted `=y`.** Despite the name it is GPT support in `block/partitions/efi.c` (GPT originated in the EFI spec), it is `default y` independently of `CONFIG_EFI`, and this image is GPT — that is the entire reason U-Boot is written at 128 KiB instead of the traditional 8 KiB. Losing it means a kernel that cannot see the data partition and a `root=UUID=` that never resolves. It is in `MUST_HAVE` so the two symbols can never be conflated.
  - **`CFG80211`/`MAC80211` are modular on purpose, and `=y` there cannot work anyway.** `config CFG80211` is `depends on RFKILL || !RFKILL`, so it is capped at `RFKILL`'s value (`m`) and `MAC80211` follows it — a `=y` line silently resolves to `m`. Building them in would also **fail the build**: mkinitcpio discovers firmware by reading `MODULE_FIRMWARE` out of each `.ko`, and `regulatory.db` is declared by `cfg80211` and nothing else, so a built-in cfg80211 leaves the regdb out of the initrd and trips `configure.sh`'s `VERIFY_FIRMWARE` check. The fragment additionally enables **`CFG80211_WEXT`**, which defconfig does not: ttyforce's initrd wifi scan falls back to `iwlist` when `iw dev scan` fails, `iwlist` is a wireless-extensions tool that does nothing without that symbol, and the binary is bundled by `initcpio/install/town-installer` — a hook **shared with every other image**, so removing `iwlist` to match would take a *working* fallback away from the PC/rpi builds to tidy a dead one here. It is in `MUST_HAVE` so it can't quietly go away again.
  - **A fragment line whose dependencies are unmet is a silent no-op, and several were.** `merge_config.sh` writes the line, `olddefconfig` drops it, nothing warns — so the fragment is checked by resolving it for real (`defconfig` → merge → `olddefconfig`) and diffing the request against the result, not just by reading it. That is what caught `IP_NF_NAT`/`IP_NF_TARGET_MASQUERADE` (upstream moved the legacy `nat` table behind `IP_NF_IPTABLES_LEGACY`; podman's netavark programs nftables, so the masquerade this box installs comes from `NFT_MASQ`), `NFT_CHAIN_NAT` (symbol no longer exists), `DRM_SUN4I_BACKEND` (the DE1 backend is `depends on ARM` — 32-bit only; the H700 feeds its TCON from the DE33 mixer), `HID_LOGITECH_DJ` (needs `HIDRAW`, now enabled) and `MODULE_COMPRESS_ZSTD` (needs `MODULE_COMPRESS` first — deliberately left off, since `/usr/lib/modules` sits inside the gzip squashfs and the initramfs is compressed whole, so a pre-compressed `.ko` is incompressible payload in both).
  - **`SATA_AHCI` is load-bearing and not for the hardware** — the real board has no SATA. `make/qemu.sh` attaches the four data disks as `-device ahci` + `ide-hd`, and those are the disks ttyforce provisions the persistent btrfs onto, so pruning AHCI would leave `make qemu-usb TARGET=rg35xxpro` booting to an installer with nothing to install to.
  - **Both directions are verified after `olddefconfig`, before the compile starts.** `MUST_HAVE` catches anything load-bearing that got dropped (a fragment line for a symbol with unmet dependencies is a silent no-op). `MUST_NOT_HAVE` catches the pruning silently coming undone — an upstream rename or a new defconfig entry re-selecting a platform would quietly restore the multi-hour multiplatform build with nothing in the log to say why. A symbol that no longer exists reads as "not enabled", so that check can never fail over a rename alone.
  - **The fragment is in the kernel cache key** (`install.sh`, alongside the build script and `dts/*.dts`) and in `IMAGE_SOURCES`. It has to be: it is where every config decision now lives, so omitting it would let an edited config reuse a kernel built from the previous one.
- **Cached in `.kernel-cache/`** (git-ignored), keyed on a hash of the build script, our device tree and any pin overrides. This is by far the most expensive step in the repo — a full kernel build, which under the emulated x86→aarch64 path takes hours — and its inputs are fully pinned, so it is built once per pin set and extracted in seconds thereafter. Delete the directory to force a rebuild. Build it on an aarch64 host if you can.
- **The pacstrapped kernel's mkinitcpio preset is retargeted to the built kernel**, in `configure.sh` right before `mkinitcpio -P`. ALARM's `linux-aarch64.preset` pins a **literal** `ALL_kver` string, and `build-kernel-rg35xx.sh` deletes `/usr/lib/modules/*` before installing the patched kernel's modules (deliberately — two module trees would make both `configure.sh`'s `KVER` and the preset ambiguous). `mkinitcpio -P` iterates every preset regardless, so the stale one aborted the build with "`/lib/modules/<alarm kver>` is not a valid kernel module directory" — hours in, after the kernel, U-Boot and ttyforce were all built. Only the version is rewritten: the preset's `default_image` (`/boot/initramfs-linux.img`) is what `install.sh` stages and what `extlinux.conf`'s `INITRD` names, so the filename must not move.

**Device tree:** mainline has **no `rg35xx-pro` DT** (only `-2024`, `-plus`, `-h`, `-sp`), so this repo carries one at `dts/sun50i-h700-anbernic-rg35xx-pro.dts` (the build's default `RG35XX_DTB`), compiled into the tree by the kernel build. It is **ROCKNIX's own Pro DT plus three button codes**: `-plus` base — the base they use too, since the two boards share design, PMIC, WiFi and the same 3.5" 640x480 panel — `&joypad { amux-count = <4>; }`, which is what turns the **analog sticks** on (the shared base sets 0 for the stickless Plus/2024), and the A/B swap + Menu→`KEY_A` above. The display arrives through the `-plus` include, because the patch set lands it in the shared `-2024` base. All family DTBs are staged on the FAT partition so the choice can be changed by editing `extlinux.conf` on the card; `RG35XX_DTB` overrides at build time and accepts an **absolute path** to a foreign `.dtb`. Use `…-rg35xx-h.dtb` if a unit needs the second USB host controller (`ehci1`/`ohci1`).

**Storage is USB; the network is WiFi or USB.** No RG35XX device tree enables the second card slot (`&mmc2`), so mainline sees only the boot card — the persistent btrfs ttyforce creates has to live on a USB device. Networking has two paths: the onboard **RTL8821CS SDIO WiFi** (`rtw88_8821cs`, which mainline does support and which is in the initrd with its firmware — see the WiFi bullet under Architecture Notes) and a **USB Ethernet adapter**, since the board has no Ethernet port. `configure.sh`'s `WANT_MODULES` gains the H700 storage/USB drivers (`sunxi_mmc`, `ehci_platform`, `phy_sun4i_usb`, `musb_hdrc`, …), the WiFi trio (`rtw88_8821cs`, `rtw88_sdio`, `rfkill`), the game-controller set (`rocknix_singleadc_joypad` above all — the board's only input; `gpio_keys` still covers the volume buttons), and the USB-Ethernet drivers (`r8152`, `asix`, `ax88179_178a`, CDC). The existing `modinfo` filter drops whatever isn't present for the installed kernel, so all of this is a no-op on the other builds, and `verify_initrd` fails the build if the RG35XX essentials didn't actually land in the initrd.

**Sledgehammer works through a `grub-reboot` shim.** There is no GRUB (so no `grub-reboot`/grubenv one-shot) and no Pi firmware (so no `tryboot`), but ttyforce's trigger interface is `grub-reboot "<menu title>"` and `scripts/ttyforce-getty.sh` detects only the Pi. So the RG35XX build **replaces `/usr/bin/grub-reboot`** with a shim that points `extlinux.conf`'s `DEFAULT` at the `sledgehammer` label; `scripts/sledgehammer.sh` resets it to `townos` before it wipes and reboots, which is what makes it a one-shot. It overwrites `/usr/bin/grub-reboot` rather than shadowing it from `/usr/local/bin` so it wins regardless of how ttyforce resolves the command. **The `MENU LABEL` in `install.sh` must keep matching the title in `ttyforce-getty.sh`/`ttyforce-status.sh`** — same invariant as the GRUB menuentry title.

**Unverified on hardware:** like the `RPI=1` and emulated-build paths, this is correct-by-construction from the U-Boot/mainline documentation but has not been built or booted on a real device. Expect to iterate the U-Boot version pin, the initrd module set, and the DT choice. `make qemu-usb TARGET=rg35xxpro USB_DEV=/dev/sdX` smoke-tests the *userspace* half (direct-kernel-boot under qemu `virt`: initrd, ttyforce, squashfs root) but cannot test U-Boot, the DTB, or any H700 driver.

### VM Launch (QEMU)

`make/qemu.sh` launches `qemu-system-$(uname -m)` natively by default (KVM, never a foreign ISA). The **one** exception is `make qemu-usb TARGET=aarch64|rpi` on an x86_64 host, which sets `QEMU_ARCH` to boot a foreign-arch USB stick under full-system TCG (see [Booting a physical USB](#booting-a-physical-usb-stick-make-qemu-usb) below) — same scoped, opt-in emulation exception as the cross-arch image build, and slow.

**sudo is primed once, up front.** `qemu.sh` makes ~30 scattered `sudo` calls (libvirt networking, sysctl/`ip link` on the bridge, an ACL on a raw USB device, and QEMU itself on the headless path), many inside `$(sudo … 2>/dev/null)` command substitutions where the password *prompt* goes to `/dev/null`. With a cold credential cache the first such call blocks on an invisible prompt, and the confused retries feed `pam_faillock` until the **account locks out for every session and user**. So the script runs a single visible `sudo -v` before any redirected call and hard-exits if root can't be obtained, then shadows `sudo` with a wrapper forcing `-n` (non-interactive) on every later call: if the cache lapses mid-run, sudo fails instantly and `set -e` aborts the whole launch rather than half-configuring the host. Never reintroduce a bare `sudo` inside a redirected command substitution here.

On **any host/arch**, it first ensures the VM bridge (`VM_BRIDGE`, default `virbr0`) exists before launching: on Fedora, libvirt runs as modular **socket-activated** daemons (`virtnetworkd`; `libvirtd.service` stays inactive), so nothing starts the autostart `default` network at boot and `virbr0` does not exist until libvirt is first poked. `qemu.sh` self-heals by running `virsh net-start default` (cycling the network via `net-destroy` if libvirt's state is stale — "active" but the bridge missing), waits for the bridge, and fails loudly with guidance if it can't be brought up. It also re-asserts per-launch state that doesn't survive bridge recreation: `resolvectl mdns` on the bridge (runtime-only setting) and, on firewalld hosts (Fedora — Arch/Debian don't enable firewalld by default), the `mdns` service in the `libvirt` zone — that zone allows dhcp/dns/ssh/tftp but **not** mdns and ends in a catch-all reject, so without it guest mDNS (UDP 5353) never reaches resolved and `.local`/`vm-ip` resolution silently fails. `deps.sh` adds the firewalld rule permanently (`--permanent` + reload). It also pins a **stable DHCP lease** for the VM: `qemu.sh` registers a MAC-keyed reservation (`virsh net-update default add ip-dhcp-host`) on the libvirt `default` network, mapping the VM's stable MAC (seeded from `VM_NAME`) to a fixed IP. `VM_IP` controls the address (default `192.168.122.50`); override with any address in the default network's subnet (e.g. `VM_IP=192.168.122.77`). It threads `make` → `qemu.sh` like the other `VM_*` vars. If `VM_IP` is empty or outside the subnet, `qemu.sh` falls back to a stable IP derived from `VM_NAME` (`<net>.200–.249`) and warns. Running several VMs at once requires a distinct `VM_IP` per VM — two sharing one address collide and the loser falls back to a dynamic (churning) lease. This is necessary because the guest presents a **fresh DHCP client-id (dhcpcd DUID) on every boot** — its root is read-only squashfs so the DUID isn't persisted — and dnsmasq keys leases on the client-id ahead of the MAC, so without a reservation the VM gets a new IP each boot (`.9 → .10 → …`), silently breaking `make vm-ip` and the guest's mDNS record. The reservation is best-effort, idempotent (deletes any prior entry for the MAC first), and only applied when `VM_BRIDGE` is the default network's bridge (custom bridges run no dnsmasq we manage). It takes effect on the guest's next DHCP (next boot); the proper guest-side fix is a stable MAC-based client identifier (see below). `qemu.sh` also makes the guest **inherit the host's upstream DNS**: it sets the libvirt `default` network's `<dns><forwarder>` to the host's real DHCP-provided DNS servers (found via `nmcli -g IP4.DNS` on the default-route interface, falling back to networkd lease files; loopback, the guest subnet, and `VM_IP` are filtered out). WHY: the network's dnsmasq (the guest's DHCP/DNS at `192.168.122.1`) otherwise resolves via the host's `/etc/resolv.conf` → systemd-resolved, so if the host points resolved at the guest (using Town OS as *its* resolver) the path **loops** — the guest's bootstrap resolver → `192.168.122.1` → host resolved → guest → … — and DNS collapses under load. (The guest queries `192.168.122.1` via its *bootstrap resolver* — used before rolodex is up and as a rolodex-down fallback; rolodex itself recurses from the roots and never forwards to it.) Pinning the forwarders breaks the loop: the guest keeps querying `192.168.122.1`, but dnsmasq (running **on the host**, so it reaches those servers exactly as the host does — the NAT'd guest usually can't query them directly) now answers from the real upstream. It's idempotent (only rewrites/`net-define`s when the forwarder set changes), best-effort, and gated on `VM_BRIDGE` being the default network's bridge. `net-define` updates only the **persistent** network definition, so a network that is already running keeps its old forwarders (and old IPv6 state) until a cold start. `qemu.sh` therefore ends the network setup with a **drift reconcile**: it compares the live XML against the persistent one (v6 block present/absent, forwarder set) and, when they disagree, `net-destroy` + `net-start`s the network so this guest boots with the current config — but **only when no other VM tap is attached to the bridge** (the bridge's own `<bridge>-nic` stub doesn't count), since destroying a live network would cut co-running VMs. With another VM present it leaves the network alone and prints the manual `virsh net-destroy default && virsh net-start default`. Stale forwarders are not cosmetic: after a WiFi change the running dnsmasq still points the guest's DNS at the previous network's servers. `qemu.sh` also gives the guest **IPv6**: it adds a ULA `/64` (`VM_NET6_PREFIX`, default `fd00:c0a8:7a::/64`; `::1` is the gateway) to the libvirt `default` network, which makes dnsmasq advertise it via **SLAAC** (libvirt auto-generates `dhcp-range=<prefix>::1,ra-only` — RA only, no DHCPv6). The guest then auto-configures a **stable EUI-64 address from its fixed MAC**, which `qemu.sh` computes and prints (`<prefix>::5054:ff:fe<last-3-MAC-octets>`). SLAAC rather than a v6 DHCP reservation **because** DHCPv6 keys leases on the guest's churning DUID and libvirt can't pin a v6 lease by MAC the way it can for IPv4 (the same DUID problem the IPv4 reservation above works around) — whereas SLAAC from the stable MAC is deterministic, so the address is known without any reservation. Like the DNS forwarders, the IPv6 `<ip>` block is written only to the **persistent** network definition (via `net-define`) and goes live via the drift reconcile above. **The v6 reconcile runs in both directions** — it adds the block when the host has working v6 and **strips** it when it doesn't. The removal half is load-bearing: a ULA block left behind by an earlier run on a v6-capable network makes libvirt advertise a v6 default route it does **not** NAT, so the guest's happy-eyeballs/AAAA path reaches for dead v6 and ttyforce's initrd reports "can't connect externally" even though IPv4 NAT works fine. **The IPv6 setup is gated on the host actually reaching the IPv6 internet:** `qemu.sh` offers the guest v6 only when a probe (ping to a couple of public v6 anycast resolvers — two, so a single filtered target isn't a false negative) succeeds from the host. Merely having a global-unicast address on the uplink is not enough — a network can advertise a v6 prefix and default route yet silently drop v6 traffic (common on managed WiFi), and libvirt's default network does not NAT IPv6 anyway, so the NAT'd ULA would be dead weight. When the probe fails (no v6 route, or v6 filtered upstream — the standard dev VM and ttyforce setups) the guest v6 is **skipped**. The probe costs at most the `-W` timeout on a half-broken-v6 network, is sub-second when v6 works, and fails instantly on a pure-IPv4 host. Set `VM_NET6_FORCE=1` to offer the guest v6 without probing; set `VM_NET6_PREFIX=` (empty) to skip IPv6 unconditionally; set `VM_IP6` to override the printed guest address (e.g. if you statically assign one in the guest). This lets rolodex and Town OS be reached and configured over IPv6 as well as IPv4.

**Both arches now open a graphical window** — x86_64 no longer uses the old headless `sudo … -nographic` serial path. The UEFI-firmware bullet is aarch64-only (e.g. Fedora Asahi on Apple Silicon); everything else below applies to both:

- **KVM is used whenever the guest arch equals the host arch and `/dev/kvm` exists** (`-enable-kvm -cpu host`) — on x86_64 **and** aarch64 (incl. Apple Silicon / Asahi, where KVM does work); otherwise `-cpu max` under TCG. On aarch64 this is not just a speed-up: under pure TCG a full aarch64 UEFI boot (firmware → GRUB → kernel) is so slow the guest takes *minutes* to even initialize the framebuffer, so the window stays blank ("Display output is not active"). With KVM the kernel boots in ~2 s and paints `tty0` immediately. (A blank screen on aarch64 is almost always missing firmware or missing KVM — not a GTK/compositor bug.) A **foreign** guest arch (`QEMU_ARCH` ≠ host, i.e. `make qemu-usb TARGET=aarch64|rpi` on x86) can never use KVM — the host CPU can't virtualize another ISA — so it falls through to TCG regardless of `/dev/kvm`, and `qemu.sh` says so.
- **UEFI firmware is mandatory.** `qemu-system-aarch64 -machine virt` has no built-in BIOS, so without edk2 via `-pflash` it never boots the image's `/EFI/BOOT/BOOTAA64.EFI` and the display is blank. `qemu.sh` locates the installed edk2 code+vars pair and gives each VM a private writable varstore copy. It **prefers the SILENT/release build** (`/usr/share/edk2/aarch64/QEMU_EFI-silent-pflash.raw`) over Fedora's default `QEMU_EFI-pflash.raw`, which is a verbose DEBUG firmware that spews symbols over serial and boots slower.
- **Graphical guests run as the invoking user, NOT root.** A root QEMU can connect to the user's Wayland socket but the compositor will not map a window owned by a different UID, so nothing shows. Running as the user maps the window normally; root is unnecessary because the bridge attaches via the setuid `qemu-bridge-helper`, the boot source is opened read-only (`snapshot=on`), and KVM needs no privilege beyond `/dev/kvm` access (which the user has). Only a display-less (`-nographic`) launch keeps `sudo` for QEMU itself.
- **The root-owned boot image is opened `snapshot=on`** so the unprivileged user can read it (it is mode 0644, world-readable but not writable) — guest writes go to a throwaway overlay and the installed image stays pristine. Consequence: writes to the boot USB (e.g. `/boot` kernel updates) are **discarded on shutdown**; the four data disks (`disk0–3.img`, user-owned, read-write) persist normally.
- **Display device is arch-specific.** aarch64 `virt` has no VGA, so it gets `-device virtio-gpu-pci -display gtk` and the guest kernel's `virtio_gpu` DRM driver provides the `console=tty0` framebuffer. x86_64 uses the PC machine's built-in VGA — just `-display gtk`, no virtio-gpu. Serial is still exported on a unix socket for `make serial` on both.
- **USB HID (`-device usb-kbd -device usb-tablet` on the `qemu-xhci` controller) is attached on BOTH arches, for different reasons.** On aarch64, `virt` has no built-in keyboard/mouse at all (that's a PC/PS2 thing) — without these the window receives no input and the ttyforce installer TUI can't be driven. On x86_64 the PS/2 devices exist but the PS/2 **mouse is a *relative* pointer**, which forces QEMU's GTK display to grab and confine the host cursor; under Wayland/Hyprland that grab drops inconsistently, the pointer lands outside the window, and focus-follows-mouse silently moves **keyboard** focus off the VM. The guest then looks frozen mid-typing when it is merely no longer being sent input — worst during long entries like the installer's GitHub-username field. `usb-tablet` reports **absolute** coordinates, so no grab is ever needed; PS/2 stays as a fallback. Guest-side USB-HID drivers come from the mkinitcpio **`keyboard`** hook that `scripts/configure.sh` enables (plus `xhci_pci`/`xhci_hcd` in `WANT_MODULES`), so input works in the initrd installer too.
- **The HMP monitor is exported on `/tmp/town-os-monitor.sock`** on every path that has a window or runs backgrounded (the headless foreground path reaches the monitor through the stdio mux, `Ctrl-a c`, so it exports no socket). Connect with `socat - UNIX-CONNECT:/tmp/town-os-monitor.sock`. This is the tool for "is it wedged or just not receiving input?": `screendump /tmp/s.ppm` captures the guest framebuffer regardless of whether the window ever mapped or which workspace it landed on, and `sendkey` injects input bypassing the compositor entirely.
- **Debugging blank video:** use the monitor socket above. On aarch64 `virt` the serial UART is **PL011 (`ttyAMA0`)**, not `ttyS0`. The desktop compositor here is **Hyprland**, which tiles the QEMU window onto the active workspace — check `hyprctl clients` if it seems missing.
- **`VM_CPUS` (default: `nproc` — every host core).** QEMU defaults to a single vCPU, which starves services that size worker pools to the CPU count — notably rolodex, whose tokio runtime scales to one worker, so cold recursive lookups (resolution plus the RBL/DNSBL check on the hot path) serialize and time out under load. Real hardware never sees this. Threaded `make` → `qemu.sh` as `-smp $(VM_CPUS)` (falling back to 4 where `nproc` is unavailable). This targets a **workstation**: on the foreign-arch TCG paths every vCPU is a busy host thread, and holding cores back for interactive responsiveness trades real wall-clock on a multi-hour build for a comfort nobody is present to enjoy. Drop it (`VM_CPUS=4`) if you do need the host while one runs.
- **`USB_PHONE` passes a physical phone through to the guest** (`auto`, `vid:pid`, or `bus.port`) — this is passthrough of a *live* device, not a stick to boot from (that's `USB_DEV`). Enable USB tethering on the phone and the box gets a direct link to it with no libvirt NAT in the path. The **host loses the phone while the VM holds it** (adb included), which otherwise looks like a failed cable.

#### Booting a physical USB stick (`make qemu-usb`)

`make qemu-usb USB_DEV=/dev/sdX` boots an **already-flashed** stick in QEMU instead of the built image — it does **not** build anything. The device is opened `snapshot=on`, so guest writes are discarded and the physical stick is never modified; the four `disk0–3.img` data disks are still attached. On the graphical path QEMU runs as the invoking user, so the script grants that user read access to the raw device for the run via `setfacl` (falling back to `chmod o+r`) rather than permanent `disk`-group membership.

`TARGET` selects the **guest architecture** here (via `BUILD_ARCH` → `QEMU_ARCH`): no `TARGET` boots natively with KVM; `TARGET=aarch64` or `TARGET=rpi` on an x86_64 host boots the stick under full-system `qemu-system-aarch64` TCG so a foreign-arch stick can be tested without foreign hardware (slow).

`TARGET=rg35xxpro` is the same **direct-kernel-boot** escape hatch as `TARGET=rpi`, one step further removed: that image's bootloader is U-Boot in the card's *raw sectors*, which only an Allwinner BootROM reads, and there is no EFI binary for edk2 to find either. So `qemu.sh` mounts the FAT partition, takes `Image` + `initramfs-linux.img` + the `APPEND` line of `extlinux.conf`'s first (`townos`) label, and hands them to `-kernel`/`-initrd`/`-append`, rewriting `console=ttyS0` → `console=ttyAMA0` (the H700's 8250 does not exist on `virt`, whose UART is a PL011). Because that cmdline names no framebuffer console at all, the guest console goes to the GTK `vc` tab exactly as on the Pi path. This exercises the initrd, ttyforce and the squashfs root on the same kernel the image ships — it does **not** exercise U-Boot, the DTB, or any H700 driver, since `virt` is not an H700.

**A real game controller is passed through to that guest** (`GAMEPAD`, default `auto` — auto-detected for an RG35XX guest only). This matters more than it sounds: that installer is driven *entirely* by a gamepad (ttyforce reads it through gilrs/evdev, and its on-screen keyboard — the only way to type on a device with no keyboard — is raised by Start), so emulating the image without one tests the boot but not the part most likely to be wrong. `qemu.sh` finds the pad by udev's own `ID_INPUT_JOYSTICK=1` classification and attaches it with **`-device virtio-input-host-pci,evdev=…`**, which forwards the host evdev node with its capability bitmaps intact — so the guest sees `BTN_SOUTH`/`BTN_DPAD_*` exactly as the handheld presents them and gilrs classifies it as a gamepad. QEMU has no synthetic gamepad device, and a `usb-kbd` would exercise the wrong input path entirely; virtio-input-host also works for Bluetooth pads, which USB passthrough cannot do. The guest needs `CONFIG_VIRTIO_INPUT` (enabled and verified in the patched kernel; `virtio_input` is in `configure.sh`'s module list for the other images). The device is opened **read-write** because virtio-input-host grabs it (`EVIOCGRAB`), so — like `USB_PHONE` — **the host cannot use the controller while the VM holds it**. `GAMEPAD=/dev/input/eventN` forces a specific device on any target; `GAMEPAD=0` disables it.

`TARGET=rpi` is further special. A Pi image has **no UEFI bootloader** — real Pi GPU firmware loads `kernel8.img` straight off the FAT partition — and QEMU `virt` can't run that firmware flow, so booting it through edk2 just drops to the UEFI shell. `qemu.sh` instead **direct-kernel-boots**: it mounts the stick's FAT partition (GPT part 2), extracts `kernel8.img` + `initramfs-linux.img` + `cmdline.txt`, and hands them to `-kernel`/`-initrd`/`-append`. Two launch-time edits to that cmdline (the image on the stick is untouched):

- `console=serial0` → `console=ttyAMA0` — `serial0` is a Pi-firmware alias that doesn't exist on `virt`, whose PL011 is `ttyAMA0`.
- **`console=tty1` is dropped.** The `linux-rpi` kernel drives only real Pi display hardware (vc4/v3d/pl111) and has no driver for *any* display QEMU `virt` can emulate — no virtio_gpu, no bochs, no VGA, no simpledrm — so `tty1` can never get a framebuffer here. The town-installer hook points ttyforce at the **last** console, so leaving `tty1` last launches ttyforce on a dead framebuffer, it exits 1, and the boot wedges with no root provisioned.

Because that kernel can drive no emulated display, the Pi guest's serial console is routed to a GTK **`vc` tab** (`-serial vc` with `-display gtk,show-tabs=on`) — switch to the "serial0" tab in the window to see and drive the installer. The virtio-gpu tab is present but inert, and there is no serial socket, so `make serial` does not apply on that path. For a real graphical framebuffer console, use `TARGET=aarch64`, whose `linux-aarch64` kernel has `virtio_gpu`.

### Host DNS Through the VM (`VM_DNS`)

Every `make qemu*` target depends on **`vm-dns`**, which points the **host's** systemd-resolved at the guest (`VM_DNS`, default `$(VM_IP)` = `192.168.122.50`) so the workstation resolves through **rolodex** exactly as a real client on the network would — split-horizon `.home` names included — instead of through its own DHCP resolver. `make/host-dns.sh set|unset` is the whole implementation. `VM_DNS=0` opts out.

- **Configuring resolved is only half of it — resolved has to be IN THE PATH.** glibc does not ask resolved anything; it reads `/etc/resolv.conf`. On a host where that is a real file written by NetworkManager (`resolvectl status` → **`resolv.conf mode: foreign`**, the default on Arch/Manjaro with no `dns=` setting) it lists the DHCP servers **directly**, so every lookup goes straight past resolved to the ISP's resolver and the VM is never consulted. This fails *silently and convincingly*: `resolvectl status` still shows the VM as the global server, because in foreign mode resolved is merely **reading that same file**. So `host-dns.sh` also points `resolv.conf` at resolved's stub for the duration, recording what was there (symlink target, or the file's bytes in `/run/town-os-host-dns.resolv*`) and restoring it — **type included** — on revert. The stub is used rather than writing `nameserver <VM_DNS>` straight into `resolv.conf` because it keeps resolved as the broker, so mDNS/LLMNR still resolve the guest's `.local` name instead of being bypassed along with everything else. **The restore must not `cp` onto the path**: at that point `resolv.conf` *is* our symlink, and `cp` follows it — it would write the backup **through** the link into resolved's stub file, corrupting it and leaving `resolv.conf` a symlink forever. It restores via a temp file + `mv -fT`, which replaces the link atomically and never leaves the host with no `resolv.conf`.
- **NetworkManager can take it back.** In its default `dns=default` mode NM *owns* `resolv.conf` and rewrites it on the next connectivity change. Nothing here can prevent that without a permanent change to the host's configuration, which is not this script's business, so it **warns once** and names the fix (`dns=systemd-resolved` in `NetworkManager.conf`) rather than making it.
- **It is a config drop-in, not `resolvectl`.** `resolvectl dns` only takes a **link**, and resolved exposes **no D-Bus method for setting the global server list** — global DNS is configuration-only. So `host-dns.sh` writes `/run/systemd/resolved.conf.d/zz-town-os-vm.conf` and reloads resolved over D-Bus (`ReloadUnit`, never the systemctl CLI). It leads with an empty **`DNS=` reset line** for the same reason `scripts/bootstrap-dns.sh` does inside the image: resolved **concatenates `DNS=` across drop-ins**, so without the reset the host's baked servers survive beside the VM and resolved can latch onto the wrong one.
- **The resolved config lives in `/run`, not `/etc`** — it is dev-VM state, not a host configuration change, so it evaporates on reboot and a workstation can never be left permanently pointed at a VM that no longer exists. (Same "no host side effects" line the rest of `qemu.sh` walks: runtime-only network state, re-asserted per launch.) The one exception is `/etc/resolv.conf` itself, which has to be repointed for any of it to take effect — that one is backed up in `/run` and restored on revert, and NM regenerates it at boot regardless.
- **The uplink's link-level DNS is cleared too, because PER-LINK DNS OUTRANKS GLOBAL.** A link with DHCP-provided servers and a default route is a candidate for every name, so writing the global list *alone* changes nothing on a normal machine. `host-dns.sh` runs `resolvectl dns <uplink> ""` + `resolvectl domain <uplink> ""` and records the link name in `/run/town-os-host-dns.link`; `unset` does `resolvectl revert` on **that recorded link**, not on whatever the default route happens to be later (WiFi roam, VPN, dock). The strip is re-asserted on **every** launch, since NetworkManager/networkd re-push those servers on any lease renewal or reconnect and would silently take resolution back. `Domains=~.` on the drop-in makes the VM the route of last resort for every name.
- **No resolver loop.** The guest's bootstrap resolver queries `192.168.122.1` — libvirt's dnsmasq, running **on the host** — which would normally forward via the host's resolv.conf → resolved → back to the guest. `qemu.sh` already breaks that by pinning the network's `<dns><forwarder>` to the host's real upstream servers (see the DNS-forwarder discussion under [VM Launch](#vm-launch-qemu)), and rolodex itself recurses from the roots. This is precisely the "host points resolved at the guest" case that pinning exists for.
- **Ordering and teardown are load-bearing.** `vm-dns` is listed **last** in each target's prerequisites (`qemu: $(IMAGE) vm-dns`) so it runs *after* a possible hour-long rebuild rather than before it — make walks prerequisites left to right. For the same reason `qemu-usb`'s `USB_DEV` guard became a **prerequisite** (`check-usb-dev`) instead of its first recipe line: as a recipe line it fired only after the resolver had already been switched to a VM that was never going to launch. Undo happens on three paths — `qemu.sh`'s foreground `EXIT` trap (so `qemu-fg`/`qemu-usb` restore the host when the VM dies), `stop-qemu.sh`, and `stop.sh` **unconditionally**, which is what recovers a host left pointed at a VM that died without its trap firing. `unset` returns before touching `sudo` when there is nothing to undo, so a routine `make stop` never prompts for a password just to discover that.
- **`qemu.sh`'s foreground cleanup is ONE function and ONE `EXIT` trap** (`fg_cleanup`, covering the LAN relay *and* the DNS switch), registered up front rather than inside the relay block: a second `trap … EXIT` silently replaces the first, and the DNS switch needs undoing even when `VM_LAN=0` or a missing reserved IP kept the relay from starting.
- Caveats: the host has **no working DNS between launch and the moment rolodex is serving**, and on `make qemu-usb` against an unprovisioned stick rolodex never comes up at all — the foreground exit trap restores the host when you quit, and `VM_DNS=0` skips it. `make run` (libvirt) is **not** wired to this; only the `qemu*` targets are.

### LAN Access to the NAT'd Guest (`VM_LAN`)

The QEMU guest sits behind libvirt's NAT (`virbr0`, 192.168.122.0/24), so other devices on the wireless network — a **phone running the Town OS client** — can neither route to it nor resolve its mDNS name. A passthrough bridge is not an option on a WiFi-only host (802.11 won't carry a second MAC behind the station). `make/vm-relay.sh` bridges the gap; it is **on by default**, and `VM_LAN=0` turns it off.

TCP and UDP need fundamentally different treatment:

- **TCP → socat.** The connection *terminates on the host* and a fresh one is opened host→guest over the bridge (always permitted), so no forwarding rules are involved at all — only the host's own INPUT is opened.
- **UDP (WireGuard) → DNAT.** socat cannot help: it is one process per port, and the WireGuard listen-port space is 4096 wide (see below). One DNAT range rule covers every network that will ever exist.

**THREE INDEPENDENT GATES REJECT INBOUND UDP TO THE GUEST, and nftables evaluates every table's chains independently — so a `reject` in ANY table is final and no `accept` in another table can rescue the packet.** All three must be handled or the phone's handshakes vanish silently (WireGuard is UDP: no error, the tunnel simply never handshakes while the client cheerfully reports "connected"):

1. **firewalld** (`inet firewalld`): `iifname "<lan>" oifname "virbr0" ... reject`. The accept must live in firewalld's own table. Two things that look like they work and DO NOT: `firewall-cmd --direct` rules land in the legacy `ip filter` table (a *different* table — its accept cannot override this reject), and `nft insert` into firewalld's table is refused with EPERM (firewalld owner-flags it). The only mechanism that expresses "from the LAN zone into the libvirt zone, accept" is a firewalld **policy** (`townos-vm`), created in `deps.sh` because it needs a `--reload` — which flushes libvirt's and netavark's runtime rules, so it must be followed by `podman network reload --all`. Doing that during a VM launch would yank the rug from under a running VM.
2. **libvirt** (`ip libvirt_network`, chain `guest_input`): accepts only `established,related` and **rejects every NEW inbound connection to the guest**. This is the gate that actually eats the WireGuard handshakes. libvirt does not owner-flag its table, so `vm-relay.sh` inserts an accept ahead of that reject. libvirt rebuilds this table whenever the network is (re)started (`virsh net-destroy`/`net-start`, libvirtd restart, host reboot), so it is **re-asserted on every launch**, not set up once.
3. **conntrack** — not a gate but the same class of silent failure: **NAT is evaluated only on a flow's FIRST packet.** A phone already retrying handshakes against a broken relay holds a conntrack entry that predates the DNAT and is never translated, so it stays wedged even after the rules are correct (the DNAT rule's counter sits at 0 while packets sail past it). `vm-relay.sh` briefly collapses `nf_conntrack_udp_timeout` to expire those entries; by hand, toggling the tunnel off/on works too (new source port → new flow).

`vm-relay.sh` **tears down its own rules before adding them**, so a run that was killed without its trap firing cannot leave duplicates behind, and stale socats are `pkill`ed. Note `firewall-cmd --remove-rule` exits 0 even when the rule does not exist, so it must never be driven by a `while remove; do :; done` loop — that spins forever.

```sh
make qemu-fg            # LAN access on by default
make qemu-fg VM_LAN=0   # off
```

- **TCP** (`VM_RELAY_TCP`, default `5309 80 443 2222:22`): the **controller API on 5309** — what the Android client enrolls against — plus the UI on 80/443. ssh maps to 2222 so it doesn't shadow the host's own sshd.
- **UDP** (WireGuard): there is **one UDP port per custom network, derived from the network's NAME** — `51820 + sha256("port|"+name)[0:2] % 4096`, range 51820–55915 (`town-os/src/wireguard/ipam.go`, `ListenPortForName`). The relay cannot enumerate the box's networks (`GET /networks` needs a bearer token), so rather than guess, it DNATs the **whole range** — every network works with no names and no discovery.
- **The endpoint takes care of itself — no client override needed.** The box writes `Endpoint` into the peer config from the address the enrolling client *dialed* (the `Host` header of its own `/networks/peers/add` request — `peerEndpointHost` in `town-os/src/svc/systemcontroller/controller_networks_reconcile.go`). A phone that enrolled through this relay reached the API at `<host LAN IP>:5309`, so that is the endpoint it is handed, and the UDP DNAT below already forwards the WireGuard range on that same address. It used to derive `Endpoint` from the box's *own* view — its public IP (ipinfo.io), falling back to its LAN IP, inside QEMU `192.168.122.50` — and neither is reachable from the phone: the public IP needs a router hairpin that consumer routers don't do, and `192.168.122.50` is behind libvirt's NAT. The peer then handshaked into a void, which looks exactly like a dead tunnel (no endpoint, no handshake, zero transfer on `wg show`) and presents as "DNS doesn't work". If the box is reached by some path the DNAT does not cover, an override on the client is still available — it is just no longer the normal case.
- Lifecycle: `qemu.sh` starts the relay before QEMU (socat happily listens against a guest that isn't up yet). **`setsid` is used only in the background (`-daemonize`) case**, where qemu.sh exits while the VM lives on so the relay must outlive it; `stop-qemu.sh` reaps it via `vm-relay.pid`. In the **foreground** case it is a plain background job in qemu.sh's own session and controlling terminal, and the EXIT trap tears it down with the VM. That distinction is not cosmetic: sudo's `tty_tickets` key the credential cache to the terminal, so a `setsid`'d relay (new session, no controlling tty) misses the ticket qemu.sh primed with `sudo -v` and re-authenticates through the askpass helper — a **second, separate password prompt**. All state is runtime-only.

### Installer Image Distribution (`make push-installer`)

The compressed USB image is published to a container registry, not a file host. `make/push-installer.sh` builds a **`scratch` OCI image** from `make/Containerfile.installer` whose single layer holds the bz2 at `/town-os.img.bz2`, plus a **dummy `CMD ["/town-os.img.bz2"]`** — the website installer does `podman create` to stream the file out via `podman cp`, and a scratch image with no command makes `podman create` fail with "no command specified". The website's `curl | bash` installer (`../website/install.sh`, `public/install.sh`) `podman pull`s this image and pipes `/town-os.img.bz2` straight through `bzip2 | dd` onto the USB stick. This is the **USB disk image** channel — unrelated to the controller/rolodex/ui app images.

- **Tags are arch-suffixed**, same scheme as the other images (builds are always native, so the build arch is the right suffix). `push-installer` publishes two: `release-$(uname -m)` (rolling — what the website pulls) and `release-$(uname -m)-$(date +%Y%m%d)` (immutable, captured at push time). Per-arch tags keep x86_64 and aarch64 from clobbering each other. Override the repo/rolling tag with `INSTALLER_BASE` / `INSTALLER_TAG`. **`RPI=1` adds a `-rpi` suffix** (`release-aarch64-rpi` + dated), so the Raspberry Pi installer image is pushed to a **separate tag** and never clobbers the PC one — matching the distinct `-rpi` image filename. `make release RPI=1` builds, compresses, and pushes the Pi installer; the website installer pulls `release-aarch64-rpi` when invoked with `RPI=1` (see `../website/install.sh`).
- **`TARGET` selects the arch/flavor for the release (and for every build target).** With **no `TARGET`**, `make release` behaves exactly as before — a native release for the host arch, honoring `RPI=1`. `TARGET` is resolved at the top of the Makefile into `BUILD_ARCH` / `RPI` / `EMULATE`, so every arch-suffixed default (the `IMAGE` filename, `INSTALLER_TAG`, and the baked `CONTROLLER_IMAGE`/`ROLODEX_IMAGE`/`UI_IMAGE` tags) recomputes in tandem — no per-target re-entry; the whole `release → push-installer → build-installer → $(IMAGE).bz2 → $(IMAGE)` chain already targets the right arch/flavor (`TARGET` propagates on `MAKEFLAGS`). The same `TARGET` works on `make image`, `make image-release`, etc.:
  - `TARGET=x86_64` (aliases `x86`, `amd64`) — native PC UEFI/GRUB image. Rejected at parse on a non-x86_64 host (there is no x86 emulation path).
  - `TARGET=aarch64` (alias `arm64`) — aarch64 UEFI/GRUB image (generic Linux / Apple-Silicon VM). **Native** on an aarch64 host; on an x86_64 host built under **full-system emulation** (`EMULATE=1` → `make/image-aarch64.sh`, a whole-machine `qemu-system-aarch64` path — never binfmt/cross-compile, image-arch still equals the virtual build-host arch; slow).
  - `TARGET=rpi` — aarch64 native-boot Raspberry Pi image (sets `RPI=1`). Native on an aarch64 host, emulated on x86 (same `EMULATE=1` path).
  - `TARGET=rg35xxpro` (aliases `rg35xx`, `rg35xx-pro`, `anbernic`) — aarch64 SD image for the Anbernic RG35XX Pro / H700 handheld family (sets `RG35XX=1`). Native on an aarch64 host, emulated on x86 (same `EMULATE=1` path).
  - Every target yields a raw disk image that boots from USB by `dd` (the installer image carries the compressed `.bz2` the website flashes to a stick); `TARGET` only changes which arch/flavor and thus which `release-<arch>[-rpi]` installer tag is pushed.
- **`make release` is just `push-installer`** now — the whole chain hangs off one real file target. **`$(IMAGE).bz2` is a file target keyed on `IMAGE_SOURCES` + `.build-config`, NOT on `$(IMAGE)`**: the raw image is deleted right after compression to save disk, so depending on `$(IMAGE)` would see it missing and force a needless second full image build on every invocation. Its recipe sub-makes `$(IMAGE)` (rebuilding only if the *sources* changed), compresses, and removes the raw file. `compress-release` and `image-release` are aliases for it, and `build-installer` depends on it — so a fresh `.bz2` is reused instead of rebuilt. `make/push-installer.sh` takes a mode (`build`|`push`|`all`): **`make build-installer`** builds the OCI image only (no push), and **`make push-installer`** depends on `build-installer` so it builds then pushes. The build and push run as **`sudo podman`** — consistent with the rest of the build tooling (`make/image-container.sh`), so the images land in root's podman storage. The build context is a temp dir with the bz2 **hardlinked** in (cp fallback if cross-fs) so podman isn't handed several GB or the whole repo; the context is user-owned and root reads it fine.
- **The website owns only the pull side now.** The old build/push tooling (`../website/Makefile` `installer-image`/`installer-push`, `../website/Dockerfile`) was removed — this repo owns building and pushing the installer image. The earlier Gitea-release flow (`make/release.sh`) is gone; releases exist solely as registry tags.

## Image Build Flow

1. `make/install.sh` creates a sparse raw image with GPT: BIOS boot (1 MiB), EFI (64 MiB), ext4 data (remainder)
2. `pacstrap` bootstraps Arch with the package set in **`make/base-packages.txt`** — podman, grub, openssh, dhcpcd, parted, wpa_supplicant/iw, `wireguard-tools`, and a curated set of admin/debug utilities (inetutils, iputils, less, vim, nano, strace, tcpdump, lsof, etc.). That file is the **single source of truth**, shared with `make/Containerfile.build`, which prefetches the same list (`pacman -Sw`) into the builder image's cache so `pacstrap` doesn't re-download it every build; the arch-specific kernel and the storage-backend packages (btrfs-progs / mdadm / *-zfs) are **not** listed there — `install.sh` appends them from `uname -m` and `town-os.yaml`. Keep the two in sync by editing only `base-packages.txt`.
3. Initcpio hooks and systemd services are copied into the chroot
4. `configure.sh` runs in chroot: installs rust, builds ttyforce, runs mkinitcpio, trims firmware, removes build deps
5. systemd units are enabled via D-Bus in a Podman container (`--rootfs` + `--systemd=true --unit=basic.target`)
6. GRUB is installed for both UEFI and BIOS boot
7. Root filesystem is compressed to squashfs with gzip (`root.sfs`) on the data partition
8. Image is shrunk to actual size

## Boot Sequence

1. GRUB loads kernel + initrd from data partition
2. **town-installer hook**:
   - Starts serial console (`agetty` on ttyS0)
   - Waits for udev to settle (block devices to appear)
   - Scans for existing btrfs on data disks — if found, skips ttyforce (already provisioned)
   - Prepares dhcpcd directories and resolv.conf
   - Runs `ttyforce initrd --etc-prefix /town-os/etc/overlays/root`
   - After ttyforce: re-mounts btrfs, creates overlay dirs, masks catch-all networkd config
3. **town-squashfs hook**: loop-mounts `root.sfs`, creates tmpfs overlay, scans for btrfs and mounts `/town-os`, overlays `/etc` and `/var` with btrfs-backed upper dirs, switch_root
4. systemd starts: systemcontroller (podman), networkd, resolved (mDNS), sshd, ttyforce getty (agetty on tty1/ttyS0 with ttyforce as login program — ttyforce manages /bin/login)

## systemd Operations

All systemd operations MUST use D-Bus (`busctl`) instead of the `systemctl` CLI. During image build, systemd calls run inside a Podman container (`--rootfs` + `--systemd=true`) so nothing affects the host. Use `podman exec <container> busctl call org.freedesktop.systemd1 ...` for build-time operations. For host-side developer tooling (`deps.sh`), use `busctl call` directly.

## Architecture Notes

- **Root is read-only squashfs + tmpfs overlay.** Changes are lost on reboot unless written to `/town-os` (persistent btrfs).
- **ttyforce runs in the initrd** via `ttyforce initrd --etc-prefix /town-os/etc/overlays/root`. The `initrd` subcommand uses syscalls and dhcpcd directly (no systemd/dbus). `--etc-prefix` tells ttyforce to write network config (networkd units, resolv.conf, wpa_supplicant) directly into the btrfs overlay upper dir, so it persists across reboots. ttyforce handles disk partitioning, btrfs formatting, mounting/unmounting `/town-os`, and all networking. **All file operations that ttyforce uses to configure the machine (network config, SSH keys, etc.) must come after filesystem creation** — `/town-os` is not a real filesystem until ttyforce creates and mounts the btrfs. Any directories created before ttyforce runs are on the initrd tmpfs and get lost when the btrfs is formatted and mounted.
- **Serial console is off by default**: The default GRUB "Town OS" entry only sets `console=tty0` — the serial device is not used at all. Serial is only active when the "Town OS (Serial Console)" entry is selected (`console=<serial>,115200`). **The serial device is arch-specific**: `ttyS0` (16550) on x86_64, `ttyAMA0` (PL011) on aarch64 — there is no `ttyS0` on aarch64 `virt`. `install.sh` derives this as `SERIAL_TTY` from `uname -m` and threads it through the GRUB menu entries and the enabled/masked serial-getty instance (`town-os-serial-getty@${SERIAL_TTY}.service`). The serial getty service (`town-os-serial-getty@.service`) is gated by `ConditionKernelCommandLine=console=<serial>,115200`; the shipped unit carries the x86_64 default (`ttyS0`) and `install.sh` rewrites that line from `$SERIAL_TTY` at build time (a `sed` right after the `systemd/` rsync) so the getty's gate stays **in tandem** with the GRUB kernel `console=` parameter — both come from the same `SERIAL_TTY`, never drifting apart. ttyforce must NOT unconditionally write to the serial console; it should only use the TTY it is given (via `--tty` or the kernel `console=` parameter). **The default can be flipped at build time** with the `SERIAL_CONSOLE` env var: when set non-empty, `install.sh` sets GRUB's `set default=` to the serial entry (index 1) instead of `0`, so the image boots straight to `<serial>,115200` with no keyboard required. This only changes which entry is the *default* — all three menu entries (Town OS, Serial Console, Sledgehammer) are still present, and GRUB itself always drives both the `serial` and `console` terminals (`terminal_input/output serial console`) so it never needs a keyboard to auto-boot after the 5s timeout.
- **Persistent storage layout on `/town-os` (btrfs):**
  - `/town-os/etc/overlays/root` — overlay upper dir for `/etc`
  - `/town-os/etc/overlays/work` — overlay work dir for `/etc`
  - `/town-os/var/overlays/root` — overlay upper dir for `/var`
  - `/town-os/var/overlays/work` — overlay work dir for `/var`
  - `/town-os/containers` — podman container storage (graphroot)
- **Podman uses native btrfs/zfs driver** to avoid overlayfs-on-overlayfs (since root is already an overlay).
- **DNS**: `/etc/resolv.conf` is always a symlink to resolved's stub (`/run/systemd/resolve/stub-resolv.conf`). systemd-resolved is the broker: its baked config is `DNS=127.0.0.2 ::1` with **no public fallback** (`FallbackDNS=` is empty). Both entries (`127.0.0.2` over IPv4, `::1` over IPv6) are **rolodex** — it binds both loopbacks, so the v6 entry just gives resolved an IPv6 path to the same resolver. rolodex resolves everything recursively from the root servers (next point), so resolved is deliberately **not** given `1.1.1.1`/`8.8.8.8` — DNS never silently works via a public resolver behind rolodex's back, and on a network that filters public DNS nothing wedges on a dead upstream. When rolodex is **down**, resolved is instead pointed at **only** the DHCP resolver (see the bootstrap point below), with the rolodex loopbacks removed entirely — resolved treats `DNS=` as a *set* and latches onto one "current" server, so a DHCP resolver listed *alongside* rolodex would receive split-horizon `.home` queries and `NXDOMAIN` them, and a dead loopback listed while rolodex is down just costs a per-query timeout. It is a hard toggle keyed on rolodex's liveness, never a preference list. Nothing else edits `/etc/resolv.conf` at runtime — the systemcontroller's `ExecStartPre`/`ExecStopPost` re-assert the stub symlink defensively. Dev mode (`LOCAL_DNS`) uses 8.8.8.8 and skips rolodex.
- **rolodex resolves via a resilient fallback chain (`resolution.mode: auto`).** `../rolodex-dns` (the default, and what `scripts/rolodex-config.sh` sets explicitly) tries, in order: **(1)** recurse from the root servers; **(2)** **DoH/DoT** to public resolvers — Cloudflare/Google, DoH on **:443 preferred** (rolodex's built-in `secure_upstreams` default) because :443 survives the DPI that filters DoT's :853 and plaintext :53; **(3)** the **local forwarder** — the DHCP-provided resolver / default gateway, which `rolodex-config.sh` computes from the networkd lease + `ip route` and writes to `forwarders`; **(4)** public resolvers over plaintext :53 as a last resort. rolodex switches tiers only after a configurable grace period of failures and **flushes its cache on every switch** (cross-tier cache-poisoning guard); it prefers the sticky active tier per query and periodically probes from the top to reclaim a recovered tier. `rolodex-config.sh` only supplies the host-specific pieces (the `bind` list and the local `forwarders`); the secure/public tiers use rolodex defaults. **Two things write `rolodex.yml`, and the ownership split is load-bearing:** `rolodex-config.sh` owns the host-specific pieces (only it can enumerate the box's addresses and DHCP resolver), while the **systemcontroller owns `resolution.mode`** (the operator's choice, held in the settings DB and applied via `RewriteConfig` + a rolodex restart). Because the script runs as rolodex's `ExecStartPre` — on *every* start, including that restart — it must **preserve the `resolution.mode` already in the file** rather than hardcode one, falling back to `auto` only on a fresh box or an unrecognized value. Hardcoding `mode: auto` there clobbers the operator's choice on the very restart meant to apply it: the setting appears to save, then silently reverts. ttyforce keeps `[DHCPv4] UseDNS=no` (and the v6 equivalent) on its networkd units so DHCP DNS never gets installed as a per-link resolver that would outrank rolodex — the DHCP resolver reaches rolodex only as the tier-3 forwarder (and, separately, as the resolved **bootstrap resolver**, next point). Why this chain exists: on the "berkeley" network **outbound :53 is filtered to everything including the root servers, and :853 (DoT) is DPI-blocked too** — only DoH on :443 and the host-proxied local forwarder (`192.168.122.1`) resolve, both of which this chain uses.
- **Bootstrap resolver — DHCP DNS until rolodex is up.** rolodex is a container pulled from `quay.io` (`--pull=always`), and pulling it must resolve `quay.io` through resolved — but resolved lists rolodex first and rolodex is exactly what's being started, so at first boot nothing can resolve. `scripts/bootstrap-dns.sh` breaks this deadlock: it derives the working resolver ttyforce determined at provisioning time — the DHCP-offered DNS from the networkd lease (`/run/systemd/netif/leases/*`), then the default gateway (a DNS forwarder in NAT/home setups; on the QEMU dev VM this is libvirt's dnsmasq at `192.168.122.1`, which forwards through the host and so works even where raw outbound public DNS is filtered) — and writes resolved's `DNS=` list as a **hard toggle keyed on rolodex's liveness** (probed via `ss` — rolodex, and only rolodex, binds `127.0.0.2:53` under `--net host`): **rolodex up → `DNS=127.0.0.2 ::1`** (rolodex is resolved's *sole* resolver); **rolodex down → `DNS=<that DHCP/gateway resolver>`** only, with the loopbacks removed. It writes `/run/systemd/resolved.conf.d/zz-townos-bootstrap.conf` (the `zz-` prefix sorts it after the baked `townos.conf`), leading with an empty `DNS=` **reset line** so the drop-in fully *replaces* the baked `DNS=127.0.0.2 ::1` rather than merging with it (resolved concatenates `DNS=` across drop-ins; without the reset the loopbacks would leak into the down state), then reloads resolved (D-Bus `ReloadUnit`) **only when the list actually changed** (idempotent). Loopback is filtered out of the DHCP resolver set (no forward-to-self loop). **Why a toggle, not a preference list:** resolved treats `DNS=` as a set, picks one "current" server and sticks to it — so a DHCP resolver listed *beside* rolodex can capture split-horizon `.home` queries and `NXDOMAIN` them, and a dead loopback listed while rolodex is down just costs a per-query timeout. **When each state is written:** `town-os-bootstrap-dns.service` (`After=network-online` / `Before=town-os-system--rolodex.service`) writes the **down** state at boot so the first `--pull=always` can resolve `quay.io`; rolodex's `ExecStartPost` (`scripts/rolodex-primary-dns.sh`, which waits for `127.0.0.2:53` to come up) flips to the **up** state the moment rolodex is serving; rolodex's `ExecStopPost` reverts to the **down** state on any stop/crash/restart. **Kept current across DHCP transitions:** `town-os-rolodex-config.path` watches `/run/systemd/netif/leases` and on every lease close-write/rename triggers `town-os-rolodex-config.service` → `scripts/rolodex-reload.sh`, which re-runs `bootstrap-dns.sh` (refresh the resolver) and regenerates `rolodex.yml`, restarting rolodex **only if its config changed** — rolodex's bind list follows the host's address, so a DHCP address change rebinds it; an identical renewal is a no-op. `TryRestartUnit` (D-Bus, not the systemctl CLI) means a lease transition before rolodex has started is a no-op and rolodex's own `ExecStartPre` still does the initial generation. Only `town-os-bootstrap-dns.service` and `town-os-rolodex-config.path` are enabled (via `EnableUnitFiles` in `make/install.sh`); `town-os-rolodex-config.service` is pulled in by the path's `Unit=`.
- Rolodex MUST always run with `--net host` — it needs direct access to the host network stack to bind its DNS listeners and detect the external interface. Its bind list is generated at startup by `scripts/rolodex-config.sh`: the two loopbacks `127.0.0.2:53` and `[::1]:53` (local resolution for systemd-resolved over v4 and v6) plus a `<ip>:53`/`[<ipv6>]:53` literal for **every `scope global` address on the default-route interface** (so rolodex is reachable externally on the host's routable IPv4 **and** IPv6). The script enumerates those addresses itself (via `ip route`/`ip addr`) and emits literals rather than using rolodex's tokens: the `primary` token is **IPv4-only** (rolodex derives it from a UDP connect to 8.8.8.8) and an interface token would also hand rolodex link-local `fe80::` addresses, which can't be bound without a scope id and log a bind error every start — filtering to `scope global` drops link-local and loopback cleanly. It MUST NOT bind to `0.0.0.0` — that would conflict with podman's DNS listener. The `dns.bind` config field is a YAML list of single-key maps: `{udp: "addr"}` or `{tcp: "addr"}`; `resolve_bind_addrs` (in `../rolodex-dns/src/config.rs`) accepts a literal `ip:port`, a bracketed `[ipv6]:port`, the `primary` keyword (default-route v4), or an interface name (all of that interface's addresses).
- **Sledgehammer mode**: GRUB menu entry "Sledgehammer - Erase Permanent Storage And Reboot" sets `town.sledgehammer` kernel param, which triggers full wipe of all non-boot disks. ttyforce getty receives the entry name via `--sledgehammer-grub-entry` so it can trigger a sledgehammer reboot from the TUI. This flag must always match the exact GRUB menuentry title in `make/install.sh`.
- **`/.town` directory** holds internal mounts that back the root overlay (squashfs at `/.town/sfs`, data partition at `/.town/data`, tmpfs overlay at `/.town/overlay`). The squashfs is also exposed at `/usb`. Do not modify these.
- **`/var` overlay is mounted in the initrd, `/etc` overlay by systemd**: The `/var` overlay MUST be mounted in the initrd (town-squashfs hook) because mounting over `/var` after systemd starts breaks journald, sockets, and PID files. The mount options MUST use post-pivot paths (`/.town/sfs/var`, `/town-os/var/overlays/root`) — never `$newroot/...` — so `/proc/mounts` is clean after `switch_root`. This works because the underlying mounts (`/.town/*`, `/town-os`) are already `mount --move`d into `$newroot` before the overlay is created. The mount target itself (`$newroot/var`) still needs the prefix since we haven't pivoted yet, but the `-o` paths must be the final paths. The `/etc` overlay is mounted by `town-os-overlays.service` using the same post-pivot paths (`/.town/sfs/etc`, `/town-os/etc/overlays/root`) and runs before `local-fs.target` so it's in place before networkd/sshd/resolved start.
- **`/boot`** is bind-mounted from the data partition so kernel/GRUB updates persist.
- **Build cleanup**: `make/install.sh` uses a trap to clean up loopback devices and mounts on failure. Use `make cleanup-loopback` to manually clean stale loopback devices.
- **Image size optimization**: The base runtime ships a curated set of admin utilities (see `make/base-packages.txt`); adjust that list to tune image size. The build strips `base-devel`, `clang`, and the Rust toolchain after compiling ttyforce. It also strips **translation catalogs, docs, and man pages**: everything under `/usr/share/locale` except `en*` (glibc's *runtime* locale data in `/usr/lib/locale` is separate and already limited to `en_US.UTF-8` by `locale-gen`), and the contents of `/usr/share/{man,doc,info}` — the directories are left in place so later package installs don't fail. This is a headless appliance driven over the network/serial installer; none of it is reachable. `linux-firmware` is trimmed to only WiFi (`iwlwifi`, `ath9k`, `ath10k`, `ath11k`, `brcmfmac`, `mt76x2u`, `rtw88`, `rtw89`), Ethernet (`rtl_nic`, `tigon`, `bnxt`, `intel`, `i40e`, `ice`, `mellanox`), GPU framebuffer (`amdgpu`, `radeon`, `i915`, `nvidia`), and regulatory DB firmware (`regulatory.db`, which cfg80211 loads before it will let a radio leave the restrictive built-in world domain — note it comes from the **`wireless-regdb`** package in `base-packages.txt`, *not* from `linux-firmware`, and every wireless package lists it only as an optional dep, so it has to be requested explicitly or the RG35XX's `verify_initrd` fails on it) — **plus, automatically, every firmware file declared by a module we actually bundle** (`modinfo -F firmware` over `HAVE_MODULES`, checking `.xz`/`.zst` variants since firmware is stored compressed while modinfo reports the uncompressed name). That second pass is what keeps the curated directory list from silently drifting out of step with `MODULES=`: adding a driver now keeps its firmware without a second edit. It only matters after switch_root — the initrd got its own copies from mkinitcpio, which runs before this trim — but a module loaded at runtime reads from the root filesystem. The package cache is cleaned after all installs. Squashfs uses **gzip** (zlib) compression — squashfs zlib decompression is built into the kernel on every arch, whereas zstd squashfs support (`CONFIG_SQUASHFS_ZSTD` / the `zstd` module) is absent on the aarch64 kernel and a zstd image fails to mount at boot there; gzip keeps the compressor consistent across x86_64 and aarch64. The EFI partition is 64 MiB (minimal but safe for UEFI firmware compatibility). These optimizations target a final image under 4 GB for USB flash drives.
- **Kernel modules in initrd**: Filesystem support (`loop`, `overlay`, `squashfs`; squashfs uses built-in zlib for the gzip-compressed root, so no `zstd` module is needed), storage drivers (`ahci`, `sd_mod`, `virtio_blk`, `virtio_scsi`, `nvme`, `usb_storage`, `uas`), **game controllers and USB Ethernet** (see the two bullets below), wired network drivers (`e1000`, `e1000e`, `igb`, `ixgbe`, `i40e`, `ice`, `virtio_net`, `r8169`, `tg3`, `bnxt_en`, `mlx4_en`, `mlx5_core`), and WiFi drivers (`cfg80211`, `mac80211`, `iwlwifi`, `iwlmvm`, `ath9k`, `ath10k_pci`, `ath11k_pci`, `brcmfmac`, `mt76x2u`, `rtw88_pci`, `rtw89_pci`) are explicitly included since `autodetect` is disabled.
- **Game-controller modules are in the initrd, and that is not cosmetic on the RG35XX**: on that board the whole pad — face buttons, shoulders, D-pad, thumb clicks **and both analog sticks** — is one input device produced by the out-of-tree `rocknix_singleadc_joypad` module the patched-kernel build compiles, so without it bundled the handheld has *no* input at all, in the installer or after boot, on hardware whose only other console is an internal UART. `verify_initrd` fails the build if it is missing. `gpio_keys` stays in the list (the volume buttons remain a `gpio-keys` node, and it is the gamepad driver on the other images), `joydev` adds `/dev/input/jsN`, and `xpad` + the `hid_*` drivers (Sony/PlayStation/Nintendo/Steam/Microsoft/Logitech) cover USB gamepads on **every** image. The sticks work only because that driver walks the GPIO-selected ADC mux itself through `CONFIG_SUN20I_GPADC`; **mainline cannot read them** — its `adc-joystick`/`io-channel-mux` path is what patch `0140` removes, and the ALARM kernel builds neither `SUN20I_GPADC` nor `JOYSTICK_ADC` anyway. Note also that the buttons emit `BTN_*` gamepad codes, which the kernel VT layer does **not** translate into console keystrokes — they are visible to `evdev` consumers, not to a TUI on `tty0`.
- **WiFi firmware and modules are in the initrd, and the build FAILS if they aren't.** ttyforce provisions the network from the initrd, so its driver, transport and firmware all have to be there before switch_root. On the RG35XX that means `rtw88_8821cs` + `rtw88_sdio` (a Realtek RTL8821CS on SDIO/mmc1 — the board's only NIC) with `rtw88/rtw8821c_fw.bin`, plus `rfkill` for ttyforce's `rfkill unblock`; the SDIO host, `mmc-pwrseq-simple` and the AXP717 regulators that power the chip are built into the kernel. mkinitcpio pulls a module's firmware in automatically (it reads `MODULE_FIRMWARE`) **and** it runs before the firmware trim, so the initrd sees the full `linux-firmware` tree — two implicit behaviours the image depends on. `configure.sh` therefore **asserts** them after `mkinitcpio -P` (`verify_initrd`, gated on `RG35XX`, which `install.sh` passes into the chroot): it checks `lsinitcpio` output for each required module (accepting a name that is built in, and matching `sunxi_mmc` against a `sunxi-mmc.ko` filename) and each required firmware file, and fails the build with the exact missing names rather than shipping a card that boots to an installer with no network and no input.
- **Initrd binaries**: `ttyforce`, `dhcpcd`, `ip`, `iw`, `iwlist`, `wpa_supplicant`, `rfkill`, `ping`, `pkill`, `setsid`, `agetty`, `parted`, `partprobe`, `udevadm`, `mkfs.btrfs`, `wipefs`, `btrfs`, plus standard mount/umount/mkdir/mountpoint. WiFi tools (`iw`, `iwlist`, `wpa_supplicant`, `rfkill`) are required for ttyforce's initrd WiFi provisioning — it scans with `iw`/`iwlist`, unblocks radios with `rfkill`, and authenticates with `wpa_supplicant`.
- **dhcpcd's resolvconf hook must be in the initrd too** — `/usr/lib/dhcpcd/dhcpcd-run-hooks` plus `/usr/lib/dhcpcd/dhcpcd-hooks/20-resolv.conf` (both ship with the `dhcpcd` package already in the rootfs, so no new dependency). The runner is dhcpcd's compiled-in default `--script`, so their mere presence activates them: dhcpcd then writes the **working DHCP-provided resolver** into `/etc/resolv.conf` (and the `/run/dhcpcd/resolv.conf/<iface>.*` fragments ttyforce reads) the moment the lease binds, before ttyforce's own resolv logic runs. With only the `dhcpcd` binary bundled, resolv.conf kept the runtime hook's public DNS seed (8.8.8.8/1.1.1.1) — blocked on NAT/captive networks such as libvirt's bridge or guest WiFi — and ttyforce's GitHub SSH-key fetch (curl, which resolves via `/etc/resolv.conf`) could not resolve anything.
- **`sudo` environment**: NEVER use `sudo -E` — it leaks the entire user environment (XDG_RUNTIME_DIR, DBUS_SESSION_BUS_ADDRESS, HOME, etc.) into root processes, causing root-owned files in `/run/user/1000` and `~/.gnupg` (pacman/pacstrap uses GPG with `$HOME/.gnupg`). Use plain `sudo` and pass only specific variables needed on the command line (e.g. `sudo VAR=value command`). None of the current build/VM scripts need HOME or SSH_AUTH_SOCK.
- **SSH authorized_keys**: ttyforce writes per-user SSH keys to `/town-os/ssh/authorized_keys/{username}` (dir 755, files 644) via `--ssh-user root,status`. The image (squashfs) always ships with password auth enabled and the default `AuthorizedKeysFile` — this is the safe fallback for fresh installs with no keys. At boot, `town-os-overlays.service` checks if any keys exist in `/town-os/ssh/authorized_keys/`; if so, it rewrites sshd_config to point `AuthorizedKeysFile` at `/town-os/ssh/authorized_keys/%u` and disables password auth. This change persists in the `/etc` overlay. If no keys exist, sshd_config is untouched and password auth works normally. `AuthorizedKeysFile` MUST only point at the `/town-os` directory structure when keys are present — never `.ssh/authorized_keys`. Keys are deduplicated by ttyforce.
- **DNS bootstrap**: systemd-resolved's baked config is `DNS=127.0.0.2 ::1` with `FallbackDNS=` empty — both entries are rolodex (v4 + v6 loopback), and there is **no public fallback**. Because rolodex isn't up yet at first boot and resolved has no public server, the image would be unable to resolve `quay.io` to pull rolodex; `town-os-bootstrap-dns.service` closes that gap by toggling resolved to the DHCP-provided resolver while rolodex is down (and back to rolodex-only once it's up) — see the bootstrap-resolver bullet above. A drop-in (`no-disable.conf`) sets `RefuseManualStop=yes` so resolved can't be taken down. The systemcontroller re-asserts the resolv.conf → stub symlink in its `ExecStartPre`/`ExecStopPost` as a defensive measure, but nothing at runtime repoints resolv.conf away from the stub.
- **`StartLimitIntervalSec` belongs in `[Unit]`**: systemd silently ignores this directive if placed in `[Service]`. Always put it in `[Unit]`.
- **Service restart resilience**: Systemd services that depend on network (e.g. systemcontroller pulling container images) must use `StartLimitIntervalSec=0` to disable the start rate limit, and a reasonable `RestartSec` (e.g. 5s) to avoid spamming. Without this, systemd's default rate limit (5 starts in 10s) permanently stops restarting the service if the network isn't ready yet (e.g. DNS unavailable before rolodex is running).
- **Container image pull policy**: Both the systemcontroller and rolodex services MUST use `--pull=missing`, **NOT** `--pull=always`. `--pull=always` re-pulls on every (re)start, which deadlocks on a crash/resume: rolodex *is* the box's DNS (pulling its own image must resolve `quay.io` through resolved → rolodex, the very thing being started), and after a suspend/resume watchdog kill neither service can reach `quay.io` while the network is still reconnecting — so the pull fails, the unit never starts, and `.home` DNS (rolodex) or management (controller) stays dead until the internet returns. `--pull=missing` restarts from the already-present local image with zero network dependency, so recovery takes seconds regardless of upstream connectivity. Updates are applied deliberately, not on every restart: the UI's `POST /system-services/refresh` explicitly `podman pull`s every system-service image — the controller first (the version anchor), then rolodex (DNS), then the others (ingress, monitoring, UI — all listed by `collectSystemServices`) — *before* restarting the units, so the freshly-pulled image is already local when `--pull=missing` runs it. The controller derives every sibling tag from `TOWN_OS_TAG` (set on its systemd unit by `install.sh` from `CONTROLLER_IMAGE`), defaulting to `rc.latest-<arch>`; there is no `/town-os.tag` file and no baked-in `Version` — a stale value in either used to pin the whole fleet to an old tag even after the controller advanced. **Architecture is selected entirely by arch-suffixed image tags** (`rc.latest-$(uname -m)`, i.e. `rc.latest-x86_64` / `rc.latest-aarch64`): each repository publishes per-arch single-arch tags rather than multi-arch manifests, and since builds are always native, the build arch is the right suffix for everything the image pulls. The Makefile composes the suffix into `CONTROLLER_TAG`/`ROLODEX_IMAGE`/`UI_IMAGE`; `install.sh` carries matching defaults (from `$ARCH`) for direct invocation. **No `--platform` flag is used**: that flag only matters for pulling a *foreign* architecture from a multi-arch manifest, which this build never does (it is always native, and podman defaults to the host's own architecture). The per-arch tag is the single source of truth for which image architecture is pulled.
- **Podman API socket for the systemcontroller**: `town-os-podman-api.service` runs `podman system service -t 0 unix:///run/podman/podman.sock` as a long-running process (not socket-activated) so the host's podman REST API is always reachable. The systemcontroller container `Requires=` and `After=` this unit, and bind-mounts the socket (`-v /run/podman/podman.sock:/run/podman/podman.sock`) so it can drive sibling containers via the host podman. The host podman's graphroot remains `/town-os/containers` (set in `/etc/containers/storage.conf`), so all images and containers managed via the socket land on the persistent btrfs. The systemcontroller also bind-mounts `/var/lib/containers:/var/lib/containers:shared`; note that this is **not** the host graphroot — `/var/lib/containers` lives on the btrfs-backed `/var` overlay and is exposed as a separate persistent path distinct from `/town-os/containers`. The `:shared` propagation lets nested mounts under that path become visible across the bind in both directions. The systemcontroller's `ExecStartPre` `mkdir -p /var/lib/containers` ensures the host directory exists before podman creates the bind.
- **Always native builds; never cross-arch, never binfmt** (with ONE explicit, opt-in exception below): With **no `TARGET`** (or `TARGET` equal to the host arch) — `make image`, `image-container`, and everything downstream — the image architecture ALWAYS equals the build host's (or same-arch builder container's) architecture — x86_64 host → x86_64 image, aarch64 host → aarch64 image. Those builds MUST NEVER cross-compile, run under CPU emulation, or inspect/register/configure `binfmt_misc`. Non-Arch hosts build inside a **same-architecture** Arch container only (it supplies Arch's `pacstrap`/`mkinitcpio`, nothing more). `install.sh` keys all arch-specific choices (kernel package, GRUB target, BIOS partition) off `uname -m`.
  - **The one exception is a foreign-arch `TARGET`** (`make image TARGET=aarch64` / `TARGET=rpi` / `TARGET=rg35xxpro` on an x86_64 host; see [Emulated aarch64 Builds on x86](#emulated-aarch64-builds-on-x86-make-image-targetaarch64--targetrpi)): it produces an aarch64 image on an x86 host by running `install.sh` inside a **full-system** `qemu-system-aarch64` VM. This still honors the *intent* of the invariant — it is a whole emulated **machine**, so `install.sh` runs as native aarch64 code and image-arch still equals (virtual-)build-host-arch — and it **never** uses `binfmt_misc`, qemu-user, or a cross-compiler. It is opt-in (only when `TARGET` names a non-host arch), never on the path of a native build; the native fast path is unchanged. To produce a different-arch image without emulation, build on a host of that architecture (a native `TARGET`).
- **No host side effects**: Build and VM tasks (image, qemu, qemu-fg, run) MUST NOT install packages, modify host services, or touch the host's package manager. The `deps` target is manual-only and must never be a dependency of other targets. `pacstrap` inside `make/install.sh` uses the host's pacman database (unavoidable), but no other host state should be modified during builds.
- **NEVER run image builds or flash commands**: Claude MUST NOT run `make image`, `make image-log`, `make flash`, `make qemu-fg`, `make qemu`, `make qemu-usb`, `make run`, `make release`, `sudo make`, or any command that builds images, launches VMs, or touches USB devices. These are destructive, long-running, require root, and must only be initiated by the user. Claude may edit source files, Makefile rules, and scripts, but must leave building and flashing to the user.
- **Image freshness**: `$(IMAGE)` depends on `IMAGE_SOURCES` (a wildcard of all scripts, systemd units, initcpio hooks, town-os.yaml, and Makefile) plus `.build-config` (a stamp file tracking build-relevant variables like `CONTROLLER_IMAGE`, `TTYFORCE_DEV`, etc.). Changing a source file or passing a different variable triggers an automatic rebuild when any target that depends on the image is invoked (flash, qemu, qemu-fg, run, virtualbox).

## Testing Changes

After modifying hooks or scripts, rebuild and launch:

```sh
make clean && make qemu-fg
```

Use `IMAGE_HOSTNAME` to avoid mDNS collisions when a real Town OS instance is already running on the network, or when multiple VMs are being tested simultaneously:

```sh
IMAGE_HOSTNAME=town-os-dev make clean && make qemu-fg
```

Each VM gets its own hostname and mDNS name (e.g. `town-os-dev.local`), preventing conflicts with production or other test instances.

Use `make serial` to attach to a backgrounded VM's serial console for debugging boot issues. Network diagnostics are logged to `/town-os/network-diag.log` on the data partition by `town-os-network-diag.service` — a **long-lived recorder, not a timer-driven oneshot**: it snapshots the same `ip`/`nft`/`iptables`/`lsmod` state each interval but appends **only when the state actually changed**, and emits one journal line at boot instead of a Starting/Deactivated/Finished triple per fire. The change key is normalized to strip fields that move on their own — DHCP `valid_lft`/`preferred_lft` countdowns, nft `counter packets N bytes N`, the `iptables-save` "# Generated on <date>" header, and lsmod refcounts — so "changed" means the network changed, not that a counter ticked; the logged dump itself is the full verbatim state. Keep that normalization in step with any new command added to the snapshot, or the log goes back to filling with noise.

`make qemu-usb USB_DEV=/dev/sdX` boots an already-flashed stick without rebuilding — handy for confirming that what shipped actually boots (and, with `TARGET=aarch64|rpi`, that a foreign-arch stick does).
